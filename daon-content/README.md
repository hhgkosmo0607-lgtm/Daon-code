## 핵심 결정 요약

한눈에 보는 확정 사항입니다. 자세한 근거는 기획서를 참고하세요.

### 제품

```
타깃      바이브코딩으로 뭔가 만들지만 코드는 모르는 사람
컨셉      문법을 외워 "직접 짜기"가 아니라, AI가 준 코드를 "이해하기"
커리큘럼   지식 분류 순서가 아닌, 프로젝트 실제 여정 순서 (8단계 40레슨)
문맥      JavaScript + React (주요 바이브코딩 툴이 생성하는 스택)
```

### 기술

```
앱        React Native + Expo
백엔드     Supabase (유저 데이터만)
콘텐츠     로컬 JSON — Supabase에 콘텐츠 테이블 두지 않음
채점      Edge Function이 서버에서 확정, 클라이언트 계산은 신뢰하지 않음
보안      RLS로 progress/daily_xp/XP 컬럼 클라이언트 쓰기 차단
갱신      EAS Update로 스토어 심사 없이 콘텐츠 반영
```

### 게임화

```
XP        레슨 완료 10 + 만점 보너스 5 + 하루목표 20
          재도전은 0 (XP 파밍 방지)
          하루목표 보너스는 그날 1회만
게스트     정상 XP의 80%, 로그인 시 차액을 보너스로 환급
스트릭     Asia/Seoul 고정, 프리즈 7일마다 1개 (무료)
로그인     배치고사 본 사람 → 결과 확인 시점에 강제
          안 본 사람 → 1단계(5레슨) 완료 시점에 강제
```

### 지금 앱의 실제 상태

`submit-answer` Edge Function을 작성했습니다(`supabase/functions/submit-answer/`).
레슨을 풀면 채점·XP·스트릭을 서버가 확정하고, 진도(progress)와 다음 레슨 잠금 해제까지
반영하도록 클라이언트(레슨 화면, 결과 화면)도 함께 연결했습니다.

다만 아직 **배포하지 않았고 실제 Supabase 프로젝트로 검증하지 않았습니다.**
`README.md`의 "Phase 4 배포하기" 절차대로 배포한 뒤, 같은 곳의 검증 체크리스트를
직접 확인해야 "완료"로 표시할 수 있습니다.

**임시 처리 한 가지**: 온보딩(Phase 6)이 아직 없어서 "나중에 하기" 버튼이 존재하지
않습니다. 그 자리를 `AuthContext`가 임시로 대신해서, 세션이 없으면 앱 시작 시 자동으로
익명 로그인을 시도합니다(`features/auth/AuthContext.tsx`). 온보딩을 만들 때 이 로직을
그 화면의 버튼 핸들러로 옮겨야 합니다. 또한 "게스트로 놓친 XP를 돌려받아요" 환급
로직(`pendingBonus` 조회 API)은 이번 작업 범위에 없어 아직 없습니다 — 로그인
화면(Phase 6)을 만들 때 함께 구현해야 합니다.

## 다음에 할 일

### 1. 앱 먼저 돌려보기

```bash
# Supabase 대시보드에서
1. SQL Editor → supabase/migrations/0001_init.sql 실행
2. Authentication → Providers → Anonymous sign-ins 켜기

# 로컬에서
cp .env.example .env    # URL, anon key 입력
npm install
npx expo start          # Expo Go로 QR 스캔
```

### 2. Phase 4 — 배포하고 검증하기

코드는 작성됐습니다(`supabase/functions/submit-answer/`). 남은 건 배포와 실기기 검증입니다.

```bash
npx supabase login
npx supabase link --project-ref <프로젝트 참조 ID>
npx supabase functions deploy submit-answer
```

검증할 것 (루트 `README.md`의 체크리스트와 동일)
  - 레슨 하나(1-2)를 실제로 풀고 홈 화면에 진도·다음 레슨 잠금 해제가 반영되는지
  - 클라이언트가 progress에 직접 UPDATE 시도 → 거부되는지
  - 같은 레슨 두 번 풀어도 XP 중복 안 되는지
  - 게스트(익명) XP가 정상의 80%만 지급되는지
  - 하루 목표 보너스가 그날 1회만 지급되는지

아직 없는 것 (Phase 6 온보딩과 함께 구현 예정)
  - 배치고사 통과 시 건너뛴 레슨 행 생성 — 배치고사 자체가 없어서 보류
  - 게스트→로그인 전환 시 "놓친 XP 환급"(pendingBonus) — 로그인 화면이 없어서 보류

### 3. Phase 7 — 콘텐츠 채우기

문제은행 3개 파일의 280문제를 `content/questions/*.json`으로 변환.
변환 형식은 `문제은행_6-8단계.md`의 부록 참고.

**변환하면서 같이 처리할 것**: 현재 `order` 유형이 4문제(1.4%)뿐이라
탭 방식 컴포넌트가 거의 안 쓰이고 있어요. 순서를 다루는 레슨 5~8개를
`order`로 전환하면 문제 형식이 다양해집니다.
후보 목록은 부록의 "알려진 불균형" 항목에 정리해뒀어요.

## 남은 판단 거리

지금 결론 낼 필요는 없지만 염두에 둘 것들입니다.

**리텐션 모델이 안 맞을 가능성**
듀오링고식 매일 접속 모델은 "매일 조금씩 쌓는" 학습에 최적화돼 있는데,
바이브코딩러는 **막혔을 때만 찾는** 성향이 강할 수 있어요.
출시 후 데이터를 보고 "막혔을 때 찾아오는 앱"으로 성격 조정이 필요할 수 있습니다.

**수익 모델**
하트(생명) 시스템은 안 씁니다. 대신 꾸미기 과금을 검토하는데,
꾸미기는 남에게 보여질 때 지갑이 열리므로 리그·프로필 공개가 전제조건이에요.
에셋은 AI 생성으로 시작 → 반응 확인 → 외주 순서.
테마는 색상 값만 바꾸면 되어 그림이 불필요하므로 1차 수익 아이템으로 적합합니다.

**콘텐츠가 곧 제품**
앱 구조는 어느 학습 앱이나 비슷해요. 차별화는 전적으로 콘텐츠에서 나오므로,
280문제의 질이 성패를 가릅니다. 개발보다 콘텐츠 제작에 시간이 더 들 것으로 봐야 해요.
