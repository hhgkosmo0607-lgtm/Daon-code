# 6단계. 프로젝트가 커질 때

## 6-1. 기능끼리 서로 얽혀있다

**Q1** (choice)
> 회원가입 문구 하나를 바꿨는데 로그인이 안 됩니다. 왜 이럴까요?
- ① 두 기능이 같은 코드(예: 회원 정보를 다루는 부분)를 공유하고 있을 수 있다 ✓
- ② AI가 일부러 망가뜨렸다
- ③ 우연이다
- ④ 문구를 잘못 입력해서

**해설**: 기능들이 코드 안에서 서로 연결돼 있는 경우가 많아서, 작은 수정도 다른 곳에 영향을 줄 수 있어요.

**Q2** (choice)
> "얽혀있다"는 것을 가장 잘 보여주는 예는?
- ① 두 화면이 완전히 독립적으로 동작할 때
- ② 같은 함수를 여러 화면에서 함께 사용할 때 ✓
- ③ 색깔이 같을 때
- ④ 파일 이름이 비슷할 때

**해설**: 같은 부품을 재사용하면, 그 부품을 고칠 때 관련된 모든 곳이 영향을 받아요.

**Q3** (choice)
> 이런 얽힘 문제를 줄이려면 어떤 습관이 도움 될까요?
- ① 수정 후 관련된 다른 기능도 확인하는 습관 (3-5) ✓
- ② 아무것도 안 하는 것
- ③ 기능을 하나도 안 만드는 것
- ④ 색을 다르게 칠하는 것

**해설**: 프로젝트가 커질수록 영향 범위도 넓어져서, 3단계의 확인 습관이 더 중요해져요.

**Q4** (blank)
> 빈칸에 알맞은 것은?
> ```
> 공용으로 쓰이는 코드를 고칠 땐, ___까지 생각해야 한다
> ```
- ① 그 코드를 함께 쓰는 다른 기능들에 미칠 영향 ✓
- ② 글자 색
- ③ 파일 이름
- ④ 아무것도

**해설**: "여기만 고치면 끝"이 아니라 "이걸 같이 쓰는 데가 또 있나"를 생각하는 습관이에요.

**Q5** (choice)
> 이 상황을 AI에게 설명할 때 좋은 방식은?
- ① "왜 안 돼요"만 말한다
- ② "회원가입 문구를 바꿨는데 로그인이 안 돼요, 같은 코드를 쓰는 것 같아요"처럼 설명한다 ✓
- ③ 아무 말도 안 한다
- ④ 프로젝트를 새로 만든다

**해설**: 무엇을 고쳤고 무엇이 이상해졌는지 설명하면, AI가 공유 코드를 확인하는 방향으로 빠르게 접근해요.

**Q6** (choice)
> 프로젝트가 커질수록 이런 얽힘 문제는?
- ① 늘어나는 경향이 있다 ✓
- ② 줄어든다
- ③ 사라진다
- ④ 무관하다

**해설**: 기능이 많아질수록 서로 연결된 지점도 많아져요.

**Q7** (compare)
> 더 나은 대응은?
>
> **A** 문제가 생겨도 "원래 이런가보다" 하고 넘어간다
> **B** 무엇을 고쳤을 때 무엇이 망가졌는지 기록해두고 AI에게 구체적으로 설명한다
- ① A
- ② B ✓

**해설**: 기록하고 설명하는 습관이 프로젝트가 커질수록 큰 힘을 발휘해요.

## 6-2. 데이터는 어디 저장되나

**Q1** (choice)
> 화면을 껐다 켜도 입력했던 데이터가 남아있으려면 어디에 저장돼야 할까요?
- ① 화면(state)에만
- ② 데이터베이스 같은 별도 저장소 ✓
- ③ 저장이 필요 없다
- ④ 브라우저 이름에

**해설**: state는 화면을 새로고침하면 사라져요. 계속 남아있어야 하는 데이터는 별도로 저장해야 합니다.

**Q2** (choice)
> 아래 중 "데이터베이스에 저장해야 하는" 값은?
- ① 지금 메뉴가 열려있는지 여부
- ② 회원이 작성한 게시글 ✓
- ③ 버튼에 마우스가 올라갔는지 여부
- ④ 입력창에 지금 타이핑 중인 글자

**해설**: "나중에도 계속 봐야 하는 것"은 데이터베이스에, "지금 화면에서만 잠깐 필요한 것"은 state로 충분해요.

**Q3** (choice)
> 화면(프론트)과 저장소(백엔드/DB)가 나뉜 이유는?
- ① 화면은 보여주는 역할, 저장소는 데이터를 오래 보관하는 역할로 나눠서 관리하기 위해 ✓
- ② 그냥 관습이라서
- ③ 화면이 저장 기능이 없어서 어쩔 수 없이
- ④ 아무 이유 없다

**해설**: 화면은 컴퓨터를 끄면 사라지지만, 데이터베이스는 서버에 계속 남아있어요.

**Q4** (blank)
> 빈칸에 알맞은 것은?
> ```
> 글쓰기 버튼을 누르면, 입력한 내용이 ___ 로 전송되어 저장된다
> ```
- ① 서버(데이터베이스) ✓
- ② 다른 사람 컴퓨터
- ③ 인쇄기
- ④ 저장 안 됨

**해설**: "저장하기"는 보통 서버에 데이터를 보내서 데이터베이스에 기록하는 과정이에요.

**Q5** (choice)
> 글을 작성했는데 새로고침하니 사라졌습니다. 가장 가능성 높은 원인은?
- ① 데이터베이스에 저장하는 과정이 빠져있거나 실패했을 가능성 ✓
- ② 인터넷이 원래 이렇게 동작한다
- ③ 글자 수가 너무 많아서
- ④ 색깔이 이상해서

**해설**: 저장 로직이 빠졌으면 화면엔 잠깐 보였다가 새로고침하면 사라져요.

**Q6** (choice)
> 2단계에서 배운 "프론트와 백엔드"가 여기서 어떻게 이어지나요?
- ① 화면(프론트)에서 입력받은 걸, 백엔드를 거쳐 데이터베이스에 저장하는 흐름으로 연결된다 ✓
- ② 전혀 관계 없다
- ③ 프론트만으로 모든 저장이 끝난다
- ④ 백엔드가 화면을 그린다

**해설**: 프론트가 데이터를 모아 백엔드로 보내고, 백엔드가 데이터베이스에 기록하는 흐름이에요.

**Q7** (compare)
> 데이터가 사라지는 문제를 AI에게 설명할 때 더 나은 방식은?
>
> **A** `"저장이 안 돼요"`
> **B** `"글쓰기 버튼을 눌러도 새로고침하면 내용이 사라져요, 데이터베이스에 저장하는 부분이 빠진 것 같아요"`
- ① A
- ② B ✓

**해설**: 증상과 추측 원인을 함께 담으면 AI가 저장 로직부터 확인하는 방향으로 접근해요.

## 6-3. 로그인이 되는 원리

**Q1** (choice)
> 로그인에 성공하면, 앱은 "이 사람이 로그인했다"는 걸 어떻게 계속 기억할까요?
- ① 매번 새로 물어본다
- ② 로그인 상태를 나타내는 정보(토큰/세션)를 저장해두고 계속 사용한다 ✓
- ③ 기억하지 않는다
- ④ 화면 색으로 표시한다

**해설**: 서버가 "인증됐다"는 증표를 내려주고, 앱은 그걸 저장했다가 이후 요청마다 함께 보내요.

**Q2** (choice)
> 로그아웃을 하면 무슨 일이 일어날까요?
- ① 그 증표를 지워서, 더 이상 로그인한 사람으로 인식되지 않게 한다 ✓
- ② 아무 일도 안 일어난다
- ③ 계정이 삭제된다
- ④ 인터넷이 끊긴다

**해설**: 로그아웃은 계정을 지우는 게 아니라 "로그인했다는 증표"만 없애는 거예요.

**Q3** (choice)
> 로그인해야만 볼 수 있는 화면을 구분하는 이유는?
- ① 개인정보나 회원 전용 기능을 보호하기 위해 ✓
- ② 랜덤으로 정해서
- ③ 화면 디자인 때문에
- ④ 이유 없음

**해설**: "내 정보 수정" 같은 화면은 본인 확인 없이 아무나 접근하면 안 돼요.

**Q4** (blank)
> 빈칸에 알맞은 것은?
> ```
> 로그인 확인 없이 아무나 "내 정보 수정" 화면에 접근할 수 있다면 ___ 위험이 있다
> ```
- ① 다른 사람 정보가 노출되거나 변경될 ✓
- ② 화면이 예뻐질
- ③ 속도가 빨라질
- ④ 없음

**해설**: 인증 없이 민감한 기능에 접근 가능하면 심각한 보안 문제가 돼요.

**Q5** (choice)
> "로그인했는데 자꾸 로그인 화면으로 튕긴다"는 문제의 가능한 원인은?
- ① 로그인 증표가 제대로 저장되지 않거나 금방 만료되고 있을 가능성 ✓
- ② 비밀번호를 안 외워서
- ③ 인터넷 속도 문제
- ④ 화면 크기 문제

**해설**: 로그인 상태를 유지하는 부분에 문제가 있으면 이런 증상이 나타나요.

**Q6** (choice)
> "인증"이라는 단어를 가장 잘 설명한 것은?
- ① "이 사람이 누구인지 확인하는 절차" ✓
- ② "화면 색을 정하는 절차"
- ③ "인터넷 속도를 재는 절차"
- ④ "글자 크기를 정하는 절차"

**해설**: 로그인이 대표적인 인증 방법이에요.

**Q7** (compare)
> 로그인 문제를 AI에게 설명할 때 더 나은 방식은?
>
> **A** `"로그인이 이상해요"`
> **B** `"로그인은 성공하는데 새로고침하면 로그인이 풀려요, 로그인 상태를 유지하는 부분에 문제가 있는 것 같아요"`
- ① A
- ② B ✓

**해설**: 증상을 구체적으로 짚으면 AI가 인증 유지 로직부터 확인하는 방향을 잡아요.

## 6-4. 코드가 지저분해질 때

**Q1** (choice)
> 파일 하나가 너무 길고 복잡해졌습니다. 이럴 때 필요한 것은?
- ① 코드를 정리(리팩토링)해달라고 요청하기 ✓
- ② 무조건 처음부터 새로 만들기
- ③ 그냥 계속 쌓기
- ④ 파일을 삭제하기

**해설**: 기능은 그대로 두고 "구조만 정리해달라"고 요청하는 걸 리팩토링이라고 불러요.

**Q2** (choice)
> 리팩토링을 하면 화면에 보이는 기능은 어떻게 될까요?
- ① 기능은 그대로 유지되고, 코드 구조만 정리된다 ✓
- ② 새로운 기능이 추가된다
- ③ 기존 기능이 사라진다
- ④ 화면 디자인이 바뀐다

**해설**: 사용자 입장에선 아무것도 달라지지 않아야 정상이에요.

**Q3** (choice)
> 언제 리팩토링을 요청하면 좋을까요?
- ① 파일이 너무 길어지거나, 비슷한 코드가 여러 곳에 반복될 때 ✓
- ② 프로젝트를 시작하자마자
- ③ 절대 필요 없다
- ④ 매일 아무 때나

**해설**: 초반엔 필요 없다가도, 기능이 쌓이면서 "이거 너무 복잡한데" 싶어지는 시점이 와요.

**Q4** (blank)
> 빈칸에 알맞은 것은?
> ```
> "이 파일이 너무 길고 복잡해진 것 같은데, ___ 해줘"
> ```
- ① 기능은 그대로 두고 구조만 정리 ✓
- ② 전부 지워
- ③ 색을 바꿔
- ④ 빨리 만들어

**해설**: "기능 유지 + 구조 정리"라는 조건을 명확히 해주는 게 좋아요.

**Q5** (choice)
> 리팩토링 후 반드시 해야 할 일은?
- ① 기존 기능들이 여전히 잘 동작하는지 확인하기 ✓
- ② 아무것도 확인 안 해도 됨
- ③ 프로젝트를 삭제
- ④ 색을 바꾸기

**해설**: 구조를 바꾸는 과정에서 실수로 기능이 깨질 수도 있어요 (3-5, 6-1과 연결).

**Q6** (choice)
> 리팩토링을 미루기만 하면 나중에 생기는 문제는?
- ① 코드가 점점 더 복잡해져서 작은 수정도 어려워진다 ✓
- ② 아무 문제 없다
- ③ 자동으로 정리된다
- ④ 속도가 빨라진다

**해설**: 정리 없이 기능만 쌓으면 코드를 이해하는 것 자체가 힘들어져요.

**Q7** (compare)
> 더 나은 접근은?
>
> **A** 코드가 지저분해져도 계속 기능만 추가한다
> **B** 가끔 "정리해줘"라고 요청해서 구조를 다듬는다
- ① A
- ② B ✓

**해설**: 중간중간 정리하면 장기적으로 프로젝트를 다루기 훨씬 수월해져요.

## 6-5. 이전 상태로 되돌리기

**Q1** (choice)
> AI에게 큰 수정을 요청했는데 오히려 더 엉망이 됐습니다. 가장 안전한 대응은?
- ① 수정 전 상태로 되돌리기 ✓
- ② 그대로 밀어붙이며 계속 고치기
- ③ 프로젝트를 삭제하고 처음부터
- ④ 포기하기

**해설**: 무작정 더 고치려다 상황이 악화될 수 있어요. 잘 되던 상태로 돌아간 뒤 다시 작게 시도하는 게 안전해요.

**Q2** (choice)
> "되돌릴 수 있다"는 게 가능하려면 평소에 어떤 습관이 필요할까요?
- ① 잘 되는 상태를 중간중간 저장(백업)해두는 습관 ✓
- ② 아무것도 저장 안 하기
- ③ 항상 최신 상태만 유지하기
- ④ 백업은 필요 없음

**해설**: 되돌리려면 "돌아갈 지점"이 있어야 해요.

**Q3** (choice)
> Git의 "커밋"이라는 개념과 이 레슨의 관계는?
- ① 커밋은 "지금 상태를 저장해두는 지점"을 만드는 방법으로, 되돌리기의 기반이 된다 ✓
- ② 전혀 관계 없다
- ③ 커밋은 삭제하는 기능이다
- ④ 커밋은 AI 요청 방법이다

**해설**: 정식으로는 Git의 커밋 기능으로 이런 저장 지점을 관리해요.

**Q4** (blank)
> 빈칸에 알맞은 것은?
> ```
> 큰 수정을 시도하기 전에는 ___ 습관이 안전하다
> ```
- ① 지금 상태를 저장해두는 ✓
- ② 아무것도 안 하는
- ③ 컴퓨터를 끄는
- ④ 인터넷을 끊는

**해설**: "혹시 잘못되면 되돌릴 수 있게" 미리 준비해두는 게 핵심이에요.

**Q5** (choice)

- ④ 아무 데나 상관없다

- ③ 속도를 높이기 위해서
- ④ 필요 없는 절차다

**해설**: 로컬의 `.env`는 배포 서버로 자동으로 안 넘어가요.

**Q4** (blank)

- ② 화면 제목
- ③ 이미지 파일
- ④ 아무 파일

- ③ 컴퓨터를 재부팅한다
- ④ 아무 조치도 필요 없다

**해설**: 이미 노출된 키는 다른 사람이 봤을 수 있으니 새 키로 바꾸는 게 안전해요.

**Q6** (choice)

- 비유는 최소한만 (상자, 이름표, 레고 조각 정도)
- 해설에 **"AI에게 뭐라고 요청하면 되는지"** 포함

## 상식으로 풀리는 문제 피하기

이 앱의 문제는 "개발 지식 없이 상식만으로 맞힐 수 있으면" 실패입니다.

```
❌ 나쁜 예
   "화면을 미리 그려보면 좋은 이유는?"
   → 코드를 몰라도 정답이 뻔히 보임

⭕ 좋은 예
   [실제 AI 요청 결과를 보여주고]
   "원하던 기능이 빠진 직접적 원인은?"
   → AI 사용 경험이 있어야 정확히 짚을 수 있음
```

**핵심 원칙 2가지**
1. 추상적 질문 대신 **실제 산출물**(터미널 출력, 에러 메시지, 코드, 대화 로그)을 먼저 보여주고 해석시킨다
2. 오답도 **기술적으로 그럴듯하게** — "컴퓨터가 고장나서" 같은 허수아비 대신, 비슷하지만 다른 개념으로 혼동을 유도

## 유형별 제약

| 유형 | 제약 |
|---|---|
| `choice` | 보기 4개, 각 2줄 이내 |
| `blank` | 보기는 짧게 (칩 버튼으로 가로 배치되므로) |
| `order` | 3~5개 항목, 탭으로 올리고 내리는 방식 |
| `compare` | **한 블록당 최대 4줄**, 전체 코드 아닌 발췌만 |

`compare`의 4줄 제한이 특히 중요합니다. 비교는 스크롤 없이 한눈에 봐야 의미가 있고, 코드는 일반 텍스트보다 인지 부하가 커서 이론상 가능한 줄 수보다 적게 잡아야 합니다. 발췌만으로 판단이 안 되는 문제는 `compare` 대신 `choice`로 전환하세요.

## 알려진 불균형 — order 유형 부족

현재 280문제의 유형 분포입니다.

| 유형 | 문제 수 | 비율 |
|---|---|---|
| choice | 201 | 71.8% |
| compare | 40 | 14.3% |
| blank | 36 | 12.9% |
| **order** | **4** | **1.4%** |

`order`가 1-2, 1-4, 4-3, 4-6 네 곳에서만 쓰이고 있습니다. 탭 방식 컴포넌트를 만들어뒀는데 거의 활용되지 않는 상태예요.

**보완이 필요한 이유**: 같은 유형만 반복되면 학습자가 지루해지고, 듀오링고식 게임화의 리듬감도 떨어집니다. 문제 형식의 다양성 자체가 리텐션 요소예요.

**order로 바꾸기 좋은 후보** — "순서"나 "절차"를 다루는 레슨의 Q4~Q7:

```
1-1  뭘 만들지 정하기        아이디어 → 기능 목록 → 화면 순서
1-5  npm run dev            install → dev → 브라우저 확인
3-5  바꾼 다음 확인하는 습관   수정 → 확인 → 다음 요청
5-2  작게 나눠서 요청하기      요청 → 확인 → 다음 요청
6-5  이전 상태로 되돌리기      백업 → 시도 → 문제시 복구
7-1  세상에 내놓기           로컬 확인 → 키 점검 → 배포 → 배포 후 확인
8-3  새 기능 추가할 때 순서    작게 나누기 → 요청 → 확인 → 배포
```

이 중 5~8개를 `order`로 전환하면 비율이 3~4% 수준으로 올라갑니다. JSON 변환 작업(Phase 7) 때 함께 반영하는 걸 권장합니다.

## 단계 간 연결

레슨끼리 서로 참조하면 학습이 누적되는 느낌을 줍니다.

```
확인하는 습관    3-5 → 6-1 → 8-3
되돌리기         6-5 → 8-3 → 8-4
구체적 요청      5-1 → 이후 모든 단계의 Q7(compare)에서 재등장
에러 읽기        4-1 → 4-6 → 7-4
```

해설에 `(3-5에서 배운)` 같은 참조를 넣어 이 연결을 드러냅니다.

## JSON 변환

문제를 앱에 넣을 때는 `content/questions/{레슨번호}.json` 형식으로 변환합니다.

```json
{
  "id": "1-2-q1",
  "lessonId": "1-2",
  "type": "choice",
  "prompt": "질문 텍스트",
  "code": "코드 블록 (없으면 생략)",
  "options": ["보기1", "보기2", "보기3", "보기4"],
  "answer": 1,
  "explanation": "해설"
}
```

- `answer`는 정답 보기의 **인덱스**(0부터 시작)
- `order` 유형만 `answer`가 배열: `[0, 1, 2]`
- 변환 후 `features/lesson/data/contentRepository.ts`의 `QUESTION_BANK`에 등록
