# Daon-code 기획서 v2

> 바이브코딩하는 사람을 위한 코드 읽기 학습 앱

---

## 1. 서비스 개요

| 항목 | 내용 |
|---|---|
| 서비스명 | Daon-code (다온코드) |
| 한 줄 소개 | AI가 만든 코드를 이해하고, 프로젝트를 끝까지 굴리게 해주는 학습 앱 |
| 타깃 | 바이브코딩으로 뭔가 만들지만 코드는 모르는 사람 |
| 형태 | 모바일 앱 (듀오링고식 게임화 학습) |
| 레퍼런스 | 듀오링고 |

### 핵심 컨셉

기존 코딩 학습 앱과 결정적으로 다른 점은 목적과 순서다.

- 기존 앱: 문법을 외워서 **직접 짜기 위한** 기초. 지식 분류 순서(변수→함수→...)로 가르침
- Daon-code: AI가 준 코드를 **이해하고 프로젝트를 굴리기 위한** 기초. **실제 프로젝트 여정 순서**로 가르침

같은 `map()`을 가르쳐도 "이렇게 쓰세요"가 아니라 "이 코드에서 이게 뭘 하고 있는지 읽어보세요"로 접근한다.

### 커리큘럼 설계 원칙 (v2에서 확정)

v1에서는 지식을 분류 순서(문법→구조→에러→AI대화→설계)로 펼쳐서 레슨이 72개까지 늘어났었다. 하지만 이 순서는 "코딩을 배우는 사람"의 논리이지, "AI에게 시켜서 프로젝트를 굴리는 사람"의 논리가 아니다.

v2는 타깃이 **실제로 프로젝트 하나를 시작해서 돌아가게 만드는 여정**을 그대로 따라간다: 시작 → 받은 코드 이해 → 직접 고쳐보기 → 막힘 → 요청 → 확장 → 공개 → 유지. 그때그때 필요한 지식만, 필요한 순서에 배치한다. 그 결과 72레슨에서 **40레슨**으로 정리됐다. 뺀 것은 대부분 "직접 코드를 짜는 사람"에게나 필요하고 "AI에게 시키는 사람"에게는 과한 내용(함수 직접 작성 문법, spread 연산자, Context API 등)이다.

### 왜 이 시장이 비어 있나

기존 코딩 학습 앱(Mimo, SoloLearn 등)은 전부 "개발자 되기"를 전제로 만들어졌다. 바이브코딩하는 사람들은 다음 지점에서 막힌다.

- AI가 준 코드를 어디에 붙여넣어야 할지 모름 (개발환경)
- 코드를 읽을 줄 몰라서 뭐가 바뀐 건지 파악이 안 됨
- 에러 메시지를 못 읽어서 AI에 그대로 복붙만 반복
- 뭘 요청해야 원하는 게 나오는지 모름
- 프로젝트가 커지면 어디서부터 손대야 할지 모름
- 배포·유지보수 단계에서 완전히 처음 겪는 개념들과 마주침

## 2. 기술 스택

```
앱        React Native + Expo
백엔드     Supabase (DB + 인증 + 실시간 + Edge Functions)
콘텐츠     레슨/문제는 앱에 로컬 번들 (정적 데이터)
푸시      Expo Push Notifications
출시      Google Play 우선 → iOS 추후
```

### 선택 근거

**React Native + Expo**
- React 경험을 그대로 활용 (문법 동일, 태그만 다름)
- Expo Go로 QR 찍어 실물 테스트, 맥 없이도 빌드 가능
- 이 앱은 문제 읽고 버튼 누르는 게 전부라 성능 이슈 없음

**Supabase**
- 서버 코드를 따로 만들 필요 없음
- 인증·실시간·보안정책이 검증된 상태로 딸려옴
- 무료 티어로 월 활성유저 5만 명까지 커버

**웹뷰 포장을 안 하는 이유**
- 스트릭 유지가 핵심인데 푸시 알림이 제대로 안 붙음
- 앱스토어 심사에서 리젝 사유가 됨

### 아키텍처 원칙 (재검토 후 확정)

초기 설계는 앱이 Supabase 테이블에 직접 읽고 쓰는 구조였다. 이는 두 가지 문제를 만든다.

**문제 1 — 클라이언트가 채점/XP를 직접 계산하면 조작이 가능하다**
Supabase 클라이언트 키는 앱 안에 있어 디컴파일이나 네트워크 탭으로 추출 가능하다. 그 키로 REST API를 직접 호출하면 문제를 풀지 않고도 XP를 조작할 수 있다. 지금(리그 없음)은 티가 안 나지만, 리그·랭킹을 붙이는 순간 바로 문제가 된다. 나중에 고치려면 앱을 통째로 업데이트해야 하므로 지금 구조를 잡아둔다.

**문제 2 — 정적 콘텐츠를 매번 원격 조회하면 오프라인/속도 문제가 생긴다**
레슨·문제 데이터는 유저마다 다르지 않고 거의 안 바뀌는 정적 데이터다. 매번 원격 조회하면 네트워크가 느릴 때 로딩이 걸리고, 오프라인에서 아예 안 되며, Supabase 무료 티어는 일주일간 요청이 없으면 프로젝트가 자동 일시정지되는 특성도 있어 초기 트래픽이 적을 때 이 문제를 모르고 있다가 앱이 갑자기 안 되는 상황을 겪기 쉽다.

**그래서 데이터를 성격별로 분리한다.**

```
정적 콘텐츠 (units / lessons / questions / terms)
  → 앱에 JSON으로 번들, 또는 빌드 시 1회 받아 로컬 캐시
  → 새 레슨 추가 시에만 동기화
  → 오프라인에서도 풀이 가능

유저별 동적 데이터 (progress / XP / streak / 오답 / 복습상태)
  → Supabase 그대로 사용 (실시간성 필요)

규칙이 있는 로직 (채점 / XP 지급 / 스트릭 갱신)
  → 클라이언트가 테이블을 직접 안 건드리고 Edge Function을 거친다
  → 앱 → submitAnswer(Edge Function) → 서버에서 채점·XP계산 → 테이블 UPDATE
  → 무료 티어 월 50만 호출 포함, 비용 문제 없음
```

이 구조가 "간단함"을 해치는 게 아니라 오히려 부합한다. 매 화면마다 로딩 상태를 관리할 필요가 없어지고, 클라이언트 코드는 로컬 데이터를 읽기만 하면 된다.

### RLS(Row Level Security) — Edge Function만으로는 부족하다

Edge Function으로 채점 로직을 서버에 두는 것과, 클라이언트가 테이블에 직접 쓰기를 시도하는 걸 막는 것은 별개의 작업이다. RLS 정책을 걸어두지 않으면, 악의적인 유저가 Edge Function을 거치지 않고 Supabase 클라이언트로 `progress`, `daily_xp`, `profiles.total_xp`를 직접 조작할 수 있다.

```
progress / daily_xp / profiles(xp·streak 관련 컬럼)
  → 일반 클라이언트 권한(anon/authenticated)으로는 INSERT/UPDATE 금지
  → Edge Function(service_role 권한)만 쓰기 가능
  → 읽기(SELECT)는 본인 행(user_id = auth.uid())만 허용
```

이 정책을 Supabase 대시보드 또는 마이그레이션 SQL에 명시적으로 설정해야, Edge Function이 실제로 "유일한 쓰기 경로"가 된다.

### 익명 로그인 — 온보딩 "나중에 하기" 경로의 저장소

온보딩에서 배치고사를 거치지 않은 사람(완전 초보, 대다수)은 "나중에 하기"로 로그인 없이 바로 학습을 시작할 수 있다. 이때도 `progress`/`daily_xp`는 `user_id`가 필요하므로, Supabase의 **익명 로그인(Anonymous Auth)** 을 화면에 드러나지 않게 내부적으로 사용한다.

```
"나중에 하기" 선택 → 익명 계정 자동 생성 (user_id 발급)
  → 학습 진행, progress/daily_xp 정상 저장
  → 이후 정식 로그인(구글/카카오/이메일) 시
    Supabase의 계정 연결(link identity) 기능으로
    익명 계정의 기존 데이터를 정식 계정에 그대로 연결
```

이 처리를 빠뜨리면 "나중에 하기"로 쌓은 진도가 정식 로그인 시점에 사라진다. (배치고사를 본 사람은 결과 확인 시점에 곧바로 정식 로그인을 요구하므로 이 경로를 안 거친다 — 6번 온보딩 섹션 참고.)

### 알림 발송 — 저장만으로는 안 온다

온보딩에서 `notify_time`을 저장해도, 그 시간에 실제로 푸시를 보내주는 장치가 따로 있어야 한다. Expo Push는 "지금 보내라"고 호출하면 보내주는 도구일 뿐, 스스로 시간을 판단하지 않는다.

```
Supabase pg_cron (매시 정각 실행)
  → 그 시간을 notify_time으로 설정한 유저 목록 조회
  → Edge Function 호출 → Expo Push API로 발송
```

`pg_cron` 확장을 활성화하고, 주기적으로 실행될 Edge Function을 별도로 만들어야 한다.

### 콘텐츠 업데이트 방식 — EAS Update

레슨/문제를 앱에 JSON으로 번들하면, 콘텐츠를 추가할 때마다 앱스토어 재심사를 거쳐야 해서 "가볍게 콘텐츠만 추가한다"는 의도와 어긋난다. Expo의 **EAS Update(OTA 업데이트)** 를 사용해 JS/JSON 변경사항을 스토어 심사 없이 유저 앱에 바로 반영한다.

## 3. 학습 문맥: JavaScript + React

주요 바이브코딩 툴(Lovable, v0, Bolt 등)이 전부 React + TypeScript + Tailwind 계열 스택으로 코드를 생성한다. 예제 코드도 교과서식(`let x = 5`)이 아니라 **AI가 실제로 뱉는 형태**(`const [count, setCount] = useState(0)`)를 그대로 쓴다.

### 다국어 확장 여지

1차는 JavaScript/React 단일 트랙으로 간다. 추후 다른 언어(Python 등)를 붙일 경우, 프로젝트 여정 구조상 "2단계. 받은 코드 뭐가 뭔지" 부분만 언어별로 분기하고 나머지 단계(환경설정 이후, 막힘, AI 요청, 유지보수)는 공통으로 재사용 가능하다.

## 4. 커리큘럼 — 8단계 40레슨

지식 분류가 아니라 **바이브코딩 프로젝트 하나를 시작해서 굴리는 실제 여정** 순서로 구성한다.

### 1단계. 시작하기 전 (5레슨)

| # | 레슨 | 내용 |
|---|---|---|
| 1-1 | 뭘 만들지 정하기 | 아이디어를 한 문장으로 |
| 1-2 | 화면부터 그려보기 | 말로 설명하기 전에 그려보는 이유 |
| 1-3 | AI에게 처음 요청하기 | 첫 프롬프트 구조 |
| 1-4 | 받은 화면들이 뭔가 | 에디터 / 터미널 / 브라우저 구분 |
| 1-5 | npm run dev, 이 세 단어 | 최소한으로 켜고 끄는 법 |

설계서·아키텍처 같은 무거운 개념은 넣지 않는다. "일단 하나 만들어서 켜본다"까지만 간다.

### 2단계. 받은 코드, 뭐가 뭔지 (6레슨)

| # | 레슨 | 내용 |
|---|---|---|
| 2-1 | 파일이 왜 여러 개인가 | 컴포넌트 개념 |
| 2-2 | 값을 담는 상자 | `const`, `let` |
| 2-3 | 값의 종류 | 문자열 / 숫자 / 참거짓 |
| 2-4 | 목록과 뭉치 | 배열, 객체 |
| 2-5 | 이 코드는 왜 반복되나 | `map()` |
| 2-6 | 이 값은 어디서 왔나 | props 읽기 |

"짜는 법"이 아니라 "이미 있는 코드를 보고 뭐가 뭔지 알아보는 것"에 집중한다.

### 3단계. 직접 고쳐보기 (5레슨)

| # | 레슨 | 내용 |
|---|---|---|
| 3-1 | 버튼 색깔 하나 바꿔보기 | 코드 값을 직접 바꾸는 첫 경험 |
| 3-2 | 문구 하나 바꿔보기 | |
| 3-3 | 값이 기억되는 원리 | `useState`, 왜 눈에 안 보이게 바뀌나 |
| 3-4 | 화면이 다시 그려지는 순간 | 리렌더링 감각 |
| 3-5 | 바꾼 다음 확인하는 습관 | 다른 곳도 확인해보기 |

읽기만 하고 끝나지 않고, 아주 작은 것 하나를 직접 고쳐보게 하는 게 핵심이다. 실제 성취감을 주는 지점.

### 4단계. 막혔을 때 (6레슨)

|---|---|---|
| 4-1 | 에러는 적이 아니다 | 에러 메시지 3요소 읽는 법 |

## 5. 문제 유형 (4가지)

전부 "읽고 고르는" 형식이라 코드 실행 환경이 필요 없다.

```json
// ① 4지선다 — 개념 확인
{
  "type": "choice",
  "prompt": "이 에러 메시지는 무슨 뜻일까요?",
  "code": "TypeError: Cannot read property 'name' of undefined",
  "options": ["값이 없는데 접근했다", "...", "...", "..."],
  "answer": 0
}

// ② 빈칸 채우기
{
  "type": "blank",
  "prompt": "빈칸에 알맞은 말은?",
  "code": "이 버튼을 누르면 ___ 하도록 만들어줘",
  "options": ["팝업이 뜨게", "예쁘게", "잘"],
  "answer": 0
}

// ③ 순서 맞추기 — 탭 방식 (드래그 아님)
{
  "type": "order",
  "prompt": "로그인 기능을 만드는 순서는?",
  "options": ["화면 만들기", "입력값 확인", "서버에 요청"],
  "answer": [0, 1, 2]
}

// ④ 코드 비교 — 발췌만, 한 블록당 최대 4줄
{
  "type": "compare",
  "prompt": "AI가 잘못 짠 코드는?",
  "options": ["코드A 발췌", "코드B 발췌"],
  "answer": 1
}
```

### 문제 유형별 UI 규칙

**① choice** — 세로 버튼 4개, 선택시 테두리 강조. 보기 2줄까지 허용, 초과시 줄임표.

**② blank** — 코드 블록 안에 빈칸, 보기는 칩 버튼으로 가로 배치.

**③ order** — 드래그 대신 **탭 방식**. 아래 단어은행에서 탭하면 위로 슬라이드(150ms, spring 애니메이션 + 짧은 햅틱), 다시 탭하면 아래로. 듀오링고가 실제로 쓰는 방식이며, 작은 화면에서 손가락에 카드가 가려지는 드래그의 문제를 피할 수 있다.

**④ compare** — 코드는 전체 컴포넌트가 아니라 **차이 나는 부분만 발췌**, 한 블록당 최대 4줄(하드 제한). 이유:
1. 비교는 스크롤 없이 한눈에 봐야 의미가 있음
2. 저가 안드로이드 기기까지 고려하면 화면 가용 높이가 더 좁음
3. 코드는 일반 텍스트보다 인지 부하가 커서, 이론상 가능한 줄 수보다 훨씬 적게 잡아야 편안하게 읽힘

발췌만으로 판단이 안 되는 문제는 compare 대신 choice로 전환한다.

### 정답/오답 피드백

- 정답: 초록 배너, 짧은 확인 문구, [계속]
- 오답: 빨강 배너, 정답 표시, 해설 전문(스크롤 가능), [계속]

오답일 때만 해설을 길게 보여준다. 정답이면 바로 다음으로 넘어가게 하고, 결과 화면에서 "해설 다시 보기"를 별도 제공한다.

## 6. 온보딩

```
① 환영
   "AI로 만들다가 막힌 적 있나요?"

② 목적 선택 (복수)
   □ AI가 만든 코드를 이해하고 싶어요
   □ 에러를 스스로 해결하고 싶어요
   □ AI에게 잘 요청하고 싶어요
   □ 프로젝트를 끝까지 완성하고 싶어요

③ 수준 자가진단
   ○ 코드를 본 적이 거의 없어요          → 1-1부터 (④⑤ 건너뜀)
   ○ AI로 만들어봤지만 코드는 몰라요      → 1-1부터 (④⑤ 건너뜀)
   ○ 코드를 조금 읽을 줄 알아요           → ④ 배치고사로
   ○ 어느 정도 읽고 수정도 해요           → ④ 배치고사로

④ 배치고사 (해당자만, 5문제)
   채점 완료 → "결과를 보려면 로그인/가입이 필요합니다"
   [ 구글로 계속하기 ] [ 카카오로 계속하기 ] [ 이메일로 가입하기 ]
   ※ 이 경로는 "나중에 하기" 없음 — 로그인해야 결과 확인 + 다음 단계 진행

⑤ 하루 목표
   ○ 가볍게 5분 / ○ 보통 10분 / ○ 열심히 15분

⑥ 알림 시간 설정

⑦ 로그인 (③에서 배치고사를 안 거친 사람만 여기서 처음 로그인 화면을 본다)
   [ 구글로 계속하기 ]
   [ 카카오로 계속하기 ]
   [ 이메일로 가입하기 ]     ← 이메일/비밀번호 직접 입력
   나중에 하기               ← 이 경로에서만 존재
        │
        ▼ (나중에 하기 선택 시, 익명 계정으로 1단계 진행)
⑧ 1단계(5레슨) 완료 → 로그인 재요구 (여기서부터 "나중에 하기" 없음)
   "게스트로 놓친 XP를 돌려받아요!" [구글] [카카오] [이메일]
   → 통과해야 2단계 진입 가능
```

**로그인 시점이 두 갈래로 나뉜다.**
- **배치고사를 본 사람(어느 정도 실력 있음)**: 자기 실력을 방금 확인한 직후, 가장 결과에 관심이 큰 순간에 로그인을 요청한다. 이 경로엔 "나중에 하기"가 없다 — 결과 저장이라는 명확한 가치와 로그인이 묶여있어 자연스럽게 받아들여진다.
- **배치고사를 안 본 사람(완전 초보, 대다수)**: 아직 앱의 가치를 못 느낀 상태라 온보딩 시점엔 로그인을 강제하지 않는다. "나중에 하기"로 익명 계정으로 시작하되, **1단계(5레슨)를 다 풀면 그 시점에 로그인을 요구한다.**

```
1단계 완료 → "게스트로 놓친 XP를 로그인하면 돌려받아요!"
            [구글] [카카오] [이메일] — 여기서는 "나중에 하기" 없음
2단계부터는 로그인(또는 계속 유지되는 익명 세션 만료 전 전환)이 필수
```

**왜 1단계 끝인가**: 1단계는 코드 지식이 전혀 필요 없고 10~15분이면 끝나는 무료체험 성격의 구간이라, 잃어도 아깝지 않은 수준의 투자다. 2단계부터는 전체 40레슨 중 87%(35레슨)가 남아있는 진짜 콘텐츠라, 이 구간을 기기에만 묶인 익명 계정으로 계속 쌓게 두면 기기 분실·앱 삭제 시 손실이 너무 커진다. "방금 가치를 확인한 직후 요청한다"는 배치고사 게이트와 같은 원칙이 여기도 적용된다.

**1단계 중간에 미리 인지시키기**: 1-3(AI에게 처음 요청하기)쯤에서 닫을 수 있는 배너로 한 번 안내한다.
```
[배너, X로 닫기 가능]
"게스트 모드로 진행 중 (XP 80%) · 로그인하면 전체 XP"
```
강제 게이트가 나왔을 때 "어, 그거였구나" 하고 덜 당황하게 만드는 용도다.

**"나중에 하기"를 선택한 사람의 데이터는 어떻게 저장하나**
Supabase의 **익명 로그인(Anonymous Auth)** 을 내부적으로 사용한다. "나중에 하기"를 눌러도 화면엔 안 보이지만 익명 계정이 자동 생성되어 `user_id`가 생기고, `progress`/`daily_xp` 저장이 정상적으로 동작한다. 이후 정식으로 구글/카카오/이메일 로그인을 하면, Supabase가 제공하는 계정 연결(link identity) 기능으로 익명 계정의 데이터를 그대로 정식 계정에 이어붙인다. 이 처리가 없으면 "나중에 하기"로 쌓은 진도가 로그인 시점에 사라진다.

### 게스트(익명) XP 차등 — 로그인 전환 유도 장치 (프로토타입 값)

1단계 구간은 짧아서(최대 5레슨, 40~50XP) 손실 크기로 압박하는 효과가 거의 없다. 그래서 숫자 자체보다 **"로그인하면 이득"이라는 인식**을 심는 데 초점을 둔다.

```
게스트(익명) 계정 XP    정상의 80% 지급 (반올림)
로그인 계정 XP         100% 지급

예) 레슨 완료 10XP → 게스트 화면엔 8XP로 표시
```

**투명하게 드러낸다.** 몰래 깎으면 넛지 효과가 없고 나중에 알아채면 반감만 준다. 위의 1-3 배너가 이 안내 역할을 한다.

**전환 시 "회수" 프레이밍**: 1단계 완료 후 로그인 화면에서 "로그인하세요"가 아니라 "게스트로 놓친 XP를 돌려받아요"로 문구를 잡는다. 실제로 로그인(계정 연결) 성공 시, 그동안 게스트로 깎인 20%만큼을 **일시불 보너스로 지급**한다. 강제 로그인 화면이 "막는 벽"이 아니라 "보상 받는 순간"으로 느껴지게 하는 장치다.

```
계정 전환(link identity) 처리 흐름
  1) 로그인 화면 진입 시, 그동안 게스트로 지급된 총 XP 합계 조회
  2) 원래(100%) 받았어야 할 값과의 차액 계산 → 화면에 미리 노출
     (예: "10XP를 돌려받아요!")
  3) 로그인 성공 → 계정 연결 → 차액을 total_xp에 일시 가산
```

**배치고사 경로는 이 장치가 필요 없다.** 결과 확인 시점에 바로 로그인하므로 애초에 익명 XP를 쌓을 틈이 없다. 이 XP 차등은 순수하게 "배치고사 안 본 초보자의 1단계 구간"에만 적용된다.

**구현 메모**
```
profiles / auth 메타데이터
  is_anonymous 여부 — Supabase가 기본 제공 (user.is_anonymous)

submitAnswer Edge Function
  - is_anonymous 이면 XP × 0.8 (반올림)
  - 정식 계정이면 XP × 1.0

pendingBonus 조회 API (신규)
  - 로그인 화면 진입 시, 계정 연결 전 예상 보너스 금액을 미리 계산해 보여줌

계정 연결 시점 Edge Function
  - 게스트 지급분과 100% 기준값의 차액을 total_xp에 가산
```

### 로그인 수단별 구현 난이도

Supabase Auth 기준으로 세 가지 성격이 다르다.

| 수단 | Supabase 지원 | 비고 |
|---|---|---|
| 이메일/비밀번호 | 기본 내장 | 별도 프로바이더 설정 없이 바로 사용 가능 |
| 구글 | 네이티브 OAuth 프로바이더 | 대시보드에서 클라이언트 ID/Secret 등록만 하면 됨 |
| 카카오 | 네이티브 OAuth 프로바이더 | 카카오 디벨로퍼스에서 REST API 키 발급 후 등록. 이메일 동의항목은 비즈 앱 전환이 필요 |
| 네이버 | **미지원** | Supabase 표준 목록에 없어 직접 연동 필요. 2차로 미룸 |

1차는 **이메일/비밀번호 + 구글 + 카카오** 세 가지로 간다. 셋 다 Supabase가 표준으로 지원해서 추가 개발 부담이 적고, "계정 없이 못 써보는" 이탈도 막을 수 있다.

**주의 — React Native는 웹과 로그인 흐름이 다르다.** Supabase의 표준 OAuth 예제(`signInWithOAuth`)는 대부분 웹 기준이라, 같은 브라우저 안에서 리다이렉트가 일어나는 걸 전제로 한다. 앱 안에는 그런 브라우저가 없어서 그대로 쓰면 동작하지 않는다. RN에서는 다음 흐름이 필요하다.

```
1) expo-web-browser로 시스템 브라우저를 열어 OAuth 로그인 진행
2) 로그인 완료 후 앱으로 돌아오는 딥링크(deep link) 처리
   (expo-auth-session으로 리다이렉트 URI 등록)
3) 받은 토큰을 supabase.auth.setSession()으로 앱 세션에 반영
```

이 배선을 빠뜨리면 "버튼은 있는데 눌러도 반응 없는" 상태가 된다.

### 배치고사 (레슨 번호 v2 기준으로 갱신)

```
문제 5개, 난이도 오름차순
  Q1  변수          (2-2 수준)
  Q2  객체 접근      (2-4 수준)
  Q3  map()         (2-5 수준)
  Q4  props         (2-6 수준)
  Q5  state         (3-3 수준)

채점 = 앞에서부터 연속으로 맞힌 개수
  0개   → 1단계부터
  1~2개 → 2단계 중반부터
  3~4개 → 3단계부터
  5개   → 4단계부터
```

**연속 정답으로 채점하는 이유**: 총 정답 수로 하면 Q1을 틀리고 Q5를 찍어서 맞힌 사람이 4단계로 가버린다.

**건너뛴 레슨은 잠그지 않는다.** 막히면 스스로 앞 단계로 돌아갈 수 있어야 한다. (1단계는 코드 지식이 필요 없으므로 배치고사 결과와 무관하게 항상 열어둔다.) 구현 방식은 10번 DB 스키마의 `progress` 테이블 참고 — 통과 시점에 건너뛴 레슨들의 진도 행을 `completed=false`로 미리 만들어두는 방식으로 "잠김"과 구분한다.

## 7. 게임화 수치

```
XP
  레슨 완료 (최초 1회만)      +10 XP
  전부 정답 (최초 1회만)      +5 XP 보너스
  하루 목표 달성 (그날 1회만)  +20 XP

  ※ 이미 completed=true인 레슨을 재도전해도 XP는 지급하지 않는다
    (복습·오답노트 목적의 재도전은 허용하되 XP 파밍은 막기 위함).
    best_score는 재도전 결과로 갱신될 수 있다.
  ※ 하루 목표 보너스는 그날 처음 목표를 넘는 순간 1회만 지급한다.
    이후 같은 날 레슨을 더 풀어도 이 보너스는 추가 지급하지 않는다.

하루 목표
  가볍게 10 XP / 보통 20 XP / 열심히 30 XP

레벨
  누적 XP 100마다 1레벨

스트릭
  하루 최소 1레슨 완료 시 유지
  스트릭 프리즈: 7일마다 1개 지급, 최대 2개 보유 (무료)
```

**타임존 주의**: `last_study_date`를 서버(UTC) 기준으로 계산하면, 한국 시간 밤 11시에 학습한 게 다음날로 기록되는 등 자정 근처에서 스트릭이 잘못 계산될 수 있다. Edge Function의 스트릭 계산 로직에서 타임존을 `Asia/Seoul`로 명시적으로 고정해서 날짜를 판단해야 한다.

**스트릭 프리즈를 무료로 주는 이유**: 바이브코딩러는 매일 접속할 동기가 약하다. 하루 놓쳤다고 스트릭이 0이 되면 이탈로 이어지므로 자동 방어로 복귀 여지를 남긴다.

## 8. 암기 복습 시스템 (라이트너 박스)

레슨은 앞으로만 진행하는 선형 트랙이고, 복습은 그와 분리된 **순환 트랙**이다. 레슨을 완료하면 그 레슨의 핵심 용어가 복습 대기열에 자동으로 들어간다.

### 간격 반복 (단순화한 라이트너 박스)

```
박스1 (신규)     → 1일 후 재출제
박스2            → 3일 후
박스3            → 7일 후
박스4            → 14일 후
박스5 (완전 암기)  → 30일 후

"알아요" 선택 → 다음 박스로 이동 (간격 늘어남)
"헷갈려요" 선택 → 박스1로 리셋 (다시 자주 나옴)
```

정답 유무가 아니라 본인의 자기평가로 박스를 이동시킨다(듀오링고 방식).

### 화면

홈 상단에 "오늘의 복습 (N개)"가 있을 때만 표시. 탭하면 플래시카드 형식으로 진행 — 용어를 보여주고 탭하면 뒤집혀 정의/예시가 나오며, 하단에 [헷갈려요] [알아요] 버튼.

### 암기 대상 용어 예시

```
변수, 함수, 배열, 객체, 조건문, 반복문
컴포넌트, props, state, 리렌더링
API, 데이터베이스, 인증, 세션
커밋, 브랜치, 배포, 리팩토링
프롬프트, 와이어프레임
```

각 용어는 처음 등장한 레슨에 연결되며, 해당 레슨 완료 시 자동으로 복습 대기열에 등록된다.

## 9. 출시 범위

콘텐츠는 8단계 40레슨 **전체를 한 번에 출시**한다(단계별로 쪼개 출시하지 않음).

### 포함

- 온보딩 + 배치고사
- 8단계 40레슨 전체
- 문제 4유형
- XP / 레벨 / 스트릭
- 암기 복습 시스템
- 프로필 (통계)
- 푸시 알림
- 구글 로그인
- **전체 무료**

### 이후 과제

- 리그 / 랭킹
- 상점 / 꾸미기 (테마 → 아바타 파츠)
- 친구
- 다른 언어 트랙 추가 (Python 등)
- 네이버 로그인 (Supabase 미지원, 직접 연동 필요)

탭은 **홈 / 프로필** 2개로 시작한다.

### 수익화 방향 (확정 아님)

하트(생명) 시스템은 쓰지 않는다. "돈 안 내면 못 배우게 막는" 구조라 초보 이탈을 키운다. 대신 꾸미기 과금을 검토한다.

다만 꾸미기는 **남에게 보여질 때** 지갑이 열리므로, 리그·프로필 공개 같은 사회적 노출 기능이 전제조건이다. 즉 리그가 단순 재미 요소가 아니라 수익 구조의 기반이 된다.

에셋은 AI 생성으로 시작해 반응을 본 뒤 외주로 전환한다. AI 생성 시 스타일 통일을 위해 단순한 스타일(픽셀아트, 플랫 일러스트)을 택하고, 완성 캐릭터보다 **파츠 조합** 방식이 제작비·아이템 수·조합 재미 모든 면에서 유리하다.

테마는 색상 값만 바꾸면 되어 그림이 불필요하므로 **1차 수익 아이템으로 적합**하다.

## 10. DB 스키마 (Supabase / PostgreSQL)

> **콘텐츠 원본 위치 (최종 결정): 로컬 JSON이 원본이다.**
> `units`/`lessons`/`questions`/`terms`는 Supabase에 테이블을 두지 않는다.
> 콘텐츠 파이프라인(스프레드시트 → 스크립트 → JSON)에서 나온 JSON을
> 앱에 직접 번들하고, EAS Update로 스토어 심사 없이 갱신한다.
> 헤드리스 CMS나 Supabase 콘텐츠 테이블은 콘텐츠 제작자가 여러 명으로
> 늘어나는 시점에 재검토한다 — 지금(혼자, 단일 언어 트랙) 규모에서는
> 이중 관리 비용만 늘어난다.
> 아래 스키마의 `units`/`lessons`/`questions`/`terms`는 "데이터 구조 참고용"으로만
> 남겨두고, 실제로는 이 구조를 그대로 로컬 JSON 스키마로 사용한다.
> `progress` 이하 유저 데이터 테이블만 실제로 Supabase에 만든다.


### 설계 포인트

**`options`, `answer`를 jsonb로 둔 이유**
문제 유형 4가지의 데이터 형태가 각각 다르다(4지선다는 보기 배열, 순서맞추기는 정답이 배열). 유형마다 컬럼을 만들면 지저분해지므로 JSON으로 유연하게 받는다.

**`daily_xp`가 필요한 이유**
리그를 보류해도 스트릭 계산과 프로필 주간 그래프에 쓰인다.

**`wrong_answers`**
오답 복습 기능용. 학습 효과가 크고 구현이 쉬워 1차에 포함한다.

**`terms` / `user_term_review`**
레슨 완료 시(`progress.completed = true`) 해당 레슨의 `terms`를 `user_term_review`에 자동 추가하고 `next_review = 내일`로 세팅한다.

**`units.language`**
다국어 확장 대비. 컬럼만 미리 만들어두고 콘텐츠는 나중에 채운다.

## 12. 리스크

### 리텐션 모델이 안 맞을 가능성

듀오링고식 매일 접속 모델은 "매일 조금씩 쌓는" 학습에 최적화돼 있다. 바이브코딩러는 **막혔을 때만 찾는** 성향이 강할 수 있다. 출시 후 데이터를 보고, 필요하면 "막혔을 때 찾아오는 앱"으로 성격을 조정해야 할 수 있다. 지금 결론 낼 필요는 없다.

### 콘텐츠가 곧 제품

앱 구조는 어느 학습 앱이나 비슷하다. 차별화는 전적으로 콘텐츠에서 나오므로, 40레슨 220~280문제의 질이 성패를 가른다. 개발보다 콘텐츠 제작에 시간이 더 들 것으로 예상해야 한다.

### 단계 간 난이도 편차

여정 순서로 짰기 때문에, 예를 들어 3단계(직접 고쳐보기)는 쉽고 6단계(프로젝트가 커질 때)는 개념적으로 더 어렵다. 문제 작성 시 각 단계 안에서도 1-1 샘플에서 잡은 난이도 흐름(개념→코드에서 찾기→구분→에러 연결→판단)을 지켜야 급격한 체감 난이도 변화를 막을 수 있다.

## 13. 문제 작성 기준 (1-1 샘플에서 확정)

- 레슨당 5~7문제, 난이도 흐름: 개념 → 실제 코드에서 찾기 → 구분 → 에러 연결 → 읽는 감각 → 판단
- 예제는 무조건 React 문맥 (`let x = 5` 대신 `const [count, setCount] = useState(0)`)
- 해설에 "AI에게 뭐라고 요청하면 되는지" 포함
- 존댓말, 짧은 문장, 전문용어("선언", "할당" 등) 배제
- 오답 보기도 초보가 실제로 헷갈릴 만한 것으로 구성
- compare 유형은 전체 코드가 아닌 발췌, 한 블록 4줄 이내
