# 3단계. 직접 고쳐보기

## 3-1. 버튼 색깔 하나 바꿔보기

**Q1** (choice)
> 이 버튼 색을 파란색에서 빨간색으로 바꾸려면 어디를 고쳐야 할까요?
> ```jsx
> <button className="bg-blue-500">구매하기</button>
> ```
- ① `button`이라는 글자
- ② `bg-blue-500` 부분 ✓
- ③ `구매하기`라는 글자
- ④ `<` 기호

**해설**: `bg-blue-500`은 "배경색을 파란색 500번 진하기로"라는 뜻이에요. `bg`는 background의 줄임말입니다.

**Q2** (choice)
> 아래 코드에서 색상을 지정하는 부분은?
> ```jsx
> <div style={{ backgroundColor: "yellow", padding: "10px" }}>
>   안내문구
> </div>
> ```
- ① `div`
- ② `backgroundColor: "yellow"` ✓
- ③ `padding: "10px"`
- ④ `안내문구`

**해설**: `style={{ }}` 안에 직접 색상 값을 넣는 방식도 자주 쓰여요.

**Q3** (choice)
> 아래 둘 중 "보이는 모습"을 바꾸는 쪽은?
> ```jsx
> A: <button className="bg-blue-500">
> B: <button onClick={handleClick}>
> ```
- ① A ✓
- ② B
- ③ 둘 다 같은 방식
- ④ 둘 다 다름

**해설**: `className`은 스타일(색, 크기), `onClick`은 클릭했을 때 실행할 동작을 연결하는 부분이라 성격이 달라요.

**Q4** (blank)
> 버튼을 초록색으로 만들려면?
> ```jsx
> <button className="___">확인</button>
> ```
- ① `bg-green-500` ✓
- ② `text-green-500`
- ③ `border-green-500`
- ④ `green`

**해설**: `bg-`가 배경색, `text-`는 글자색, `border-`는 테두리색이에요.

**Q5** (choice)
> 색을 바꿨다고 생각했는데 화면에 변화가 없습니다. 가장 흔한 원인은?
- ① 파일을 저장하지 않아서 ✓
- ② React가 고장나서
- ③ 인터넷이 끊겨서
- ④ 빨간색이 존재하지 않아서

**해설**: 에디터에서 고친 내용은 저장(Ctrl+S / Cmd+S)해야 반영돼요.

**Q6** (choice)
> `bg-blue-500`에서 숫자 `500`은 무슨 의미일까요?
- ① 색상의 진하기 정도 (숫자가 클수록 진함) ✓
- ② 버튼의 크기
- ③ 클릭 횟수
- ④ 아무 의미 없는 장식

**해설**: 보통 100(연함)부터 900(진함)까지 숫자로 진하기를 표현해요.

**Q7** (compare)
> 버튼을 강조색으로 바꾸려 합니다. 더 적절한 요청은?
>
> **A** `"버튼 좀 눈에 띄게 해줘"`
> **B** `"구매하기 버튼 배경색을 bg-orange-500으로 바꿔줘"`
- ① A
- ② B ✓

**해설**: B처럼 구체적인 클래스명을 언급하면 AI가 정확히 어디를 고칠지 헷갈리지 않아요.

## 3-2. 문구 하나 바꿔보기

**Q1** (choice)
> "구매하기"를 "주문하기"로 바꾸려면 어느 부분을 고쳐야 할까요?
> ```jsx
> <button className="bg-blue-500">구매하기</button>
> ```
- ① `button`
- ② `className="bg-blue-500"`
- ③ `구매하기` ✓
- ④ `<` `>` 기호들

**해설**: 태그와 태그 사이에 있는 글자가 화면에 보이는 텍스트예요.

**Q2** (choice)
> "환영합니다!" 문구는 코드의 어디에 있을까요?
> ```jsx
> 1  function Welcome() {
> 2    return (
> 3      <div className="container">
> 4        <h1>환영합니다!</h1>
> 5      </div>
> 6    )
> 7  }
> ```
- ① 3번 줄
- ② 4번 줄 ✓
- ③ 1번 줄
- ④ 6번 줄

**해설**: `<h1>`과 `</h1>` 사이의 글자가 실제로 화면에 나타나요.

**Q3** (choice)
> 아래 중 화면에 보이는 글자가 **아닌** 것은?
> ```jsx
> <p className="title">안녕하세요</p>
> ```
- ① `안녕하세요`
- ② `title` ✓
- ③ 둘 다 보인다
- ④ 둘 다 안 보인다

**해설**: `title`은 이 태그에 붙은 이름표일 뿐, 화면에 글자로 나타나지 않아요.

**Q4** (blank)
> 화면에 "장바구니가 비어있습니다"라고 보여주려면?
> ```jsx
> <p>___</p>
> ```
- ① `장바구니가 비어있습니다` ✓
- ② `className="empty"`
- ③ `p`
- ④ `return`

**해설**: 태그 사이에 보여주고 싶은 문구를 그대로 적으면 돼요.

**Q5** (choice)
> 문구를 고쳤는데 화면에 이렇게 보입니다. 원인은?
> ```
> {환영합니다!}
> ```
- ① 중괄호 `{}`를 실수로 같이 써서, 문자 그대로 화면에 나타난 것 ✓
- ② 인터넷 문제
- ③ 폰트가 없어서
- ④ 서버가 꺼져서

**해설**: `{}`는 "여기 안에 자바스크립트 값을 넣을게"라는 특별한 기호예요. 고정된 글자엔 안 씁니다.

**Q6** (choice)
> `{userName}`처럼 중괄호로 감싸진 부분은 무엇을 의미할까요?
> ```jsx
> <p>안녕하세요, {userName}님!</p>
> ```
- ① 고정된 글자가 아니라, 변수에 담긴 값을 그 자리에 끼워 넣는 것 ✓
- ② 그냥 장식 기호
- ③ 에러가 있다는 표시
- ④ 주석(설명글)

**해설**: userName이 "김철수"라면 화면엔 "안녕하세요, 김철수님!"으로 보여요.

**Q7** (compare)
> 버튼 문구를 "다음"에서 "완료"로 바꾸려 합니다. 더 적절한 요청은?
>
> **A** `"버튼 글자 바꿔줘"`
> **B** `"'다음' 버튼을 '완료'로 바꿔줘"`
- ① A
- ② B ✓

**해설**: 버튼이 여러 개 있을 수 있으니, 어떤 버튼인지 정확히 짚어줘야 해요.

## 3-3. 값이 기억되는 원리

**Q1** (choice)
> 아래 코드에서 "지금까지 몇 번 눌렀는지"를 기억하는 부분은?
> ```jsx
> const [count, setCount] = useState(0)
> ```
- ① `useState(0)` 전체 ✓
- ② `count`만
- ③ `setCount`만
- ④ 기억하는 부분이 없다

**해설**: `useState(0)`은 "0에서 시작하는 값을 기억해줘"라는 뜻이에요. 이렇게 기억되는 값을 **state**라고 불러요.

**Q2** (choice)
> 버튼을 누르면 어떤 일이 일어날까요?
> ```jsx
> const [count, setCount] = useState(0)
>
> <button onClick={() => setCount(count + 1)}>
>   {count}
> </button>
> ```
- ① `count` 값이 1 늘어나고, 화면의 숫자도 함께 바뀐다 ✓
- ② 아무 일도 일어나지 않는다
- ③ 버튼이 사라진다
- ④ 페이지가 새로고침된다

**해설**: `setCount`가 실행되면 화면의 `{count}`도 자동으로 새 값으로 바뀌어요.

**Q3** (choice)
> 일반 변수와 `useState` 값의 결정적 차이는?
- ① 일반 변수를 바꿔도 화면이 자동으로 안 바뀌지만, useState 값은 화면이 자동으로 바뀐다 ✓
- ② 둘은 완전히 똑같다
- ③ useState는 숫자만 담을 수 있다
- ④ 일반 변수가 더 빠르다

**해설**: React에게 "이 값이 바뀌면 화면을 다시 그려줘"라고 알려주는 특별한 방법이 `useState`예요.

**Q4** (blank)
> 좋아요 개수를 기억하려면?
> ```jsx
> const [likeCount, setLikeCount] = ___(0)
> ```
- ① `useState` ✓
- ② `const`
- ③ `map`
- ④ `props`

**해설**: 값을 기억하고 화면에 반영하려면 `useState`를 씁니다.

**Q5** (choice)
> 버튼을 눌러도 화면 숫자가 안 바뀝니다. 원인은?
> ```jsx
> const [count, setCount] = useState(0)
>
> <button onClick={() => count = count + 1}>
>   {count}
> </button>
> ```
- ① `setCount`를 안 쓰고 `count`를 직접 바꾸려고 해서 ✓
- ② 버튼이 고장나서
- ③ useState를 두 번 써서
- ④ 원래 안 되는 기능이다

**해설**: 반드시 `setCount`라는 전용 도구를 통해야 React가 "값이 바뀌었으니 화면을 다시 그려야겠다"고 알아채요.

**Q6** (choice)
> `isOpen`은 어떤 값을 기억할까요?
> ```jsx
> const [isOpen, setIsOpen] = useState(false)
> ```
- ① 메뉴나 창이 열려있는지 아닌지 (참/거짓) ✓
- ② 열린 횟수 (숫자)
- ③ 열린 사람 이름
- ④ 열린 시각

**해설**: `is~`로 시작하고 초기값이 `false`면 대부분 "열림/닫힘" 같은 참거짓 상태예요.

**Q7** (compare)
> 메뉴가 열리고 닫히는 기능을 만들려 합니다. 더 적절한 코드는?
>
> **A**
> ```jsx
> let isOpen = false
> <button onClick={() => isOpen = true}>열기</button>
> ```
> **B**
> ```jsx
> const [isOpen, setIsOpen] = useState(false)
> <button onClick={() => setIsOpen(true)}>열기</button>
> ```
- ① A
- ② B ✓

**해설**: A처럼 그냥 변수로 하면 값은 바뀌어도 화면은 그대로예요.

## 3-4. 화면이 다시 그려지는 순간

**Q1** (choice)
> `setCount`로 state를 바꾸면 React는 실제로 무엇을 할까요?
- ① 바뀐 숫자 하나만 몰래 고쳐놓는다
- ② 해당 컴포넌트를 다시 실행해서, 새 값으로 화면을 다시 그린다 ✓
- ③ 페이지 전체를 새로고침한다
- ④ 아무것도 안 한다

**해설**: "리렌더링"이라고 불러요. state가 바뀌면 컴포넌트 함수가 처음부터 다시 실행됩니다.

**Q2** (choice)
> 버튼을 누를 때마다 다시 계산되는 부분은?
> ```jsx
> function Counter() {
>   const [count, setCount] = useState(0)
>   const doubled = count * 2
>
>   return (
>     <div>
>       <p>{count} / 두 배: {doubled}</p>
>       <button onClick={() => setCount(count + 1)}>+1</button>
>     </div>
>   )
> }
> ```
- ① `useState(0)`이 실행된 첫 순간만
- ② `count`가 바뀔 때마다 함수 전체(`doubled` 계산 포함)가 다시 실행된다 ✓
- ③ `button` 부분만
- ④ 아무것도 다시 계산되지 않는다

**해설**: 함수가 위에서부터 다시 실행되므로 `doubled`도 매번 새 값으로 계산돼요.

**Q3** (choice)
> "리렌더링"을 가장 잘 설명한 것은?
- ① 컴포넌트가 값이 바뀔 때마다 처음부터 다시 실행되는 것 ✓
- ② 페이지를 새로고침 버튼으로 다시 불러오는 것
- ③ 컴퓨터를 재부팅하는 것
- ④ 코드를 저장하는 것

**해설**: 브라우저 전체가 아니라, 값이 바뀐 컴포넌트만 다시 실행돼서 화면 일부가 업데이트되는 거예요.

**Q4** (blank)
> state가 바뀌면 컴포넌트가 어떻게 실행될까요?
> ```
> state가 바뀌면 컴포넌트가 ___ 다시 실행된다
> ```
- ① 처음부터 ✓
- ② 무작위로
- ③ 마지막 줄만
- ④ 절대

**해설**: 첫 줄부터 끝까지 다시 실행돼서, 함수 안의 모든 계산이 새 값으로 이뤄져요.

**Q5** (choice)
> 버튼을 빠르게 여러 번 눌렀는데 숫자가 한 번만 늘어난 것처럼 보입니다. 가능한 설명은?
- ① state 업데이트와 화면 반영 사이에 약간의 처리 시간차가 있을 수 있다 ✓
- ② 버튼이 고장났다
- ③ count가 삭제됐다
- ④ useState를 잘못 썼다 (항상 문제)

**해설**: 정말 이상하다 싶으면 "state 업데이트가 이상한 것 같은데 확인해줘"라고 AI에게 물어보면 됩니다. 지금은 "이런 것도 있구나" 정도면 충분해요.

**Q6** (choice)
> `console.log`가 버튼 누를 때마다 계속 찍힙니다. 이게 의미하는 바는?
- ① 컴포넌트가 실제로 계속 다시 실행되고 있다는 증거 ✓
- ② 코드가 무한 반복하며 고장난 것
- ③ 아무 의미 없다
- ④ 인터넷이 끊겼다는 신호

**해설**: 리렌더링이 일어날 때마다 함수 안 코드가 다시 실행되니 로그도 그때마다 찍혀요.

**Q7** (compare)
> 화면에 값이 안 바뀌는 문제를 AI에게 알릴 때 더 나은 설명은?
>
> **A** `"값이 안 바뀌어요 고쳐주세요"`
> **B** `"버튼을 눌러도 useState로 관리되는 count가 화면에 그대로예요"`
- ① A
- ② B ✓

**해설**: "어떤 값이, 어떤 방식으로 관리되는데"를 설명하면 AI가 원인을 빠르게 좁힐 수 있어요.

## 3-5. 바꾼 다음 확인하는 습관

**Q1** (choice)
> 로그인 버튼 색만 바꾸려 했는데 다른 페이지 버튼 색도 바뀌었습니다. 가장 먼저 할 일은?
- ① 그냥 넘어간다
- ② 다른 페이지들도 둘러보며 의도치 않은 변화가 없는지 확인한다 ✓
- ③ 컴퓨터를 재시작한다
- ④ AI를 다른 걸로 바꾼다

**해설**: 컴포넌트가 여러 곳에서 재사용되는 경우가 많아서(2-1), 하나를 고치면 예상 못 한 곳도 바뀔 수 있어요.

**Q2** (choice)
> "확인하는 습관"이 특히 중요한 상황은?
- ① 혼자만 쓰는 메모장 앱의 글자 크기를 바꿀 때
- ② 여러 화면에서 공통으로 쓰는 버튼 컴포넌트를 고칠 때 ✓
- ③ 앱 이름을 바꿀 때
- ④ 색상 하나를 미리보기만 할 때

**해설**: 공용 부품을 고칠수록 영향 범위가 넓어져요.

**Q3** (choice)
> "확인하는 습관"이 의미하는 것과 가장 가까운 것은?
- ① 코드를 아예 안 바꾸는 것
- ② 바꾼 후에 눈으로 직접 여러 화면을 눌러보며 이상 없는지 살피는 것 ✓
- ③ AI에게 확인을 맡기고 안 보는 것
- ④ 백업만 해두고 확인은 생략하는 것

**해설**: AI가 "다 됐어요"라고 해도 실제로 의도한 대로인지는 사람이 봐야 알아요.

**Q4** (blank)
> 수정 요청 후 좋은 습관은?
> ```
> AI가 코드를 고쳐줬다 → ___ → 이상 없으면 다음 작업으로
> ```
- ① 여러 화면을 눌러보며 확인한다 ✓
- ② 바로 다음 요청을 한다
- ③ 컴퓨터를 끈다
- ④ 코드를 전부 지운다

**해설**: 확인 없이 바로 다음 요청을 이어가면 문제가 쌓여서 나중에 원인을 찾기 어려워져요.

- ③ 확인은 생략해도 된다
- ④ AI에게 전적으로 맡긴다

**해설**: 작게 나눠서 확인하는 습관이 나중에 시간을 아껴줘요.

**Q6** (choice)

- ③ AI 사용량이 줄어든다
- ④ 디자인이 예뻐진다

**해설**: 바로바로 확인하면 원인이 방금 한 수정이라는 게 명확해요.

# 4단계. 막혔을 때

## 4-1. 에러는 적이 아니다

**Q1** (choice)
> 화면에 이런 빨간 글씨가 떴습니다. 가장 먼저 해야 할 일은?
> ```
> TypeError: Cannot read property 'name' of undefined
> ```
- ① 당황해서 전부 지우고 다시 시작한다
- ② 메시지를 천천히 읽어서 뭐가 문제인지 파악한다 ✓
- ③ 무조건 컴퓨터를 재시작한다
- ④ 못 본 척 넘어간다

**해설**: 에러 메시지는 "고장났다"는 알림이 아니라 "여기가 문제예요"라고 알려주는 힌트예요.

**Q2** (choice)
> 아래 에러에서 "종류(무슨 문제인지)"에 해당하는 부분은?
> ```
> TypeError: Cannot read property 'name' of undefined
> ```
- ① `TypeError` ✓
- ② `Cannot read property`
- ③ `'name'`
- ④ `undefined`

**해설**: 콜론(`:`) 앞부분이 에러의 종류예요. `TypeError`는 "값의 종류가 예상과 달라서 생긴 문제"라는 뜻입니다.

**Q3** (choice)
> 에러 메시지의 "위치"는 보통 어디서 확인할 수 있을까요?
- ① 에러 메시지의 색깔
- ② 메시지 아래/옆에 함께 뜨는 파일명과 줄 번호 ✓
- ③ 메시지의 글자 크기
- ④ 메시지가 뜬 시각

**해설**: 이 위치부터 살펴보면 원인을 좁히기 쉬워져요.

**Q4** (blank)
> 에러 메시지를 읽을 때 확인해야 할 3가지는?
> ```
> 종류, 위치, ___
> ```
- ① 설명(무슨 상황인지) ✓
- ② 색깔
- ③ 크기
- ④ 시간

**해설**: 종류(무슨 에러), 위치(어디서), 설명(구체적으로 뭐가 잘못됐는지)이 핵심 정보예요.

**Q5** (choice)
> 에러가 떴는데 무슨 뜻인지 전혀 모르겠습니다. 가장 좋은 다음 행동은?
- ① 에러 메시지 전체를 복사해서 AI에게 "이 에러가 뭔지 설명해줘"라고 물어본다 ✓
- ② 에러가 사라질 때까지 아무 코드나 지워본다
- ③ 프로젝트를 처음부터 새로 시작한다
- ④ 에러를 무시하고 계속 진행한다

**해설**: 완벽히 이해 못 해도 괜찮아요. 메시지 전체를 보여주면 AI가 해석해주고 고치는 방법도 알려줍니다.

**Q6** (choice)
> 아래 두 상황 중 "지금 당장 AI에게 물어봐야 할" 쪽과 "잠시 기다려봐도 되는" 쪽을 짝지으면?
> ```
> 상황 A: 코드 수정 후 저장하자마자
>         "Unexpected token" 에러가 뜸
>
> 상황 B: npm run dev를 실행했는데
>         터미널이 아무것도 안 뜨고 멈춰있음 (5분째)
> ```
- ① A=기다려도 됨, B=바로 물어봐야 함
- ② A=바로 물어봐야 함, B=일단 좀 더 기다려도 됨(초기 설치 중일 수 있음) ✓
- ③ 둘 다 즉시 물어봐야 함
- ④ 둘 다 기다려도 됨

**해설**: 문법 에러는 코드에 실제 문제가 있다는 명확한 신호지만, 처음 실행 시 멈춰 보이는 건 의존성 설치 중일 수 있어요.

**Q7** (compare)
> 에러가 났을 때 AI에게 더 나은 요청은?
>
> **A** `"에러 나요 고쳐주세요"`
> **B** `"TypeError: Cannot read property 'name' of undefined 라는 에러가 떴어요"`
- ① A
- ② B ✓

**해설**: 정확한 메시지를 그대로 전달하면 AI가 훨씬 정확하게 원인을 찾을 수 있어요.

## 4-2. 값이 없다고 나올 때

**Q1** (choice)
> 이 에러는 무슨 뜻일까요?
> ```
> Cannot read property 'name' of undefined
> ```
- ① 어떤 값이 아직 준비되지 않았는데(undefined), 그 안에서 `name`을 꺼내려고 해서 ✓
- ② name이라는 이름을 쓸 수 없어서
- ③ 인터넷이 끊겨서
- ④ 파일이 삭제돼서

**해설**: "빈 상자를 열어서 안의 물건 이름을 물어보는" 상황이에요.

**Q2** (choice)
> 아래 코드에서 에러가 날 가능성이 있는 줄은?
> ```jsx
> 1  function UserCard({ user }) {
> 2    return (
> 3      <div>
> 4        <p>{user.name}</p>
> 5      </div>
> 6    )
> 7  }
> ```
- ① 1번
- ② 4번 ✓
- ③ 3번
- ④ 6번

**해설**: `user`가 아직 안 넘어왔거나 `undefined`인 상태에서 `user.name`을 읽으려 하면 에러가 나요.

**Q3** (choice)
> `undefined`와 `null`의 공통점은?
- ① 둘 다 "값이 없음"을 나타낸다 ✓
- ② 둘 다 숫자 0을 의미한다
- ③ 둘 다 에러 메시지다
- ④ 아무 관련 없다

**해설**: 세세한 차이는 있지만, 초보 단계에선 "값이 아직 없는 상태"로 함께 이해해도 충분해요.

**Q4** (blank)
> 데이터가 아직 안 왔을 수도 있는 상황을 방어하려면?
> ```jsx
> <p>{user___name}</p>
> ```
- ① `?.` ✓
- ② `.`
- ③ `!.`
- ④ `,`

**해설**: `user?.name`은 "user가 있으면 name을 보여주고, 없으면 넘어가"라는 방어 코드예요.

**Q5** (choice)
> 상품 목록 화면에서 이 에러가 떴습니다. 가장 가능성 높은 원인은?
> ```
> Cannot read property 'price' of undefined
> ```
- ① 데이터를 아직 못 받아온 시점에, 화면이 그 데이터를 미리 읽으려고 해서 ✓
- ② 가격이 무료라서
- ③ 상품이 너무 비싸서
- ④ 화면 크기 문제

**해설**: 서버에서 데이터를 받아오는 데 시간이 걸려요. 그 사이 "아직 없는 데이터"를 읽으려 하면 이 에러가 흔히 나요.

**Q6** (choice)
> "Cannot read property 'X' of undefined" 형태의 에러에서 공통으로 짐작할 수 있는 것은?
- ① 뭔가(X 앞의 것)가 비어있는 상태에서 그 안의 값을 꺼내려 했다는 패턴 ✓
- ② 인터넷 속도가 느리다는 뜻
- ③ 디자인이 잘못됐다는 뜻
- ④ 프로젝트를 새로 만들어야 한다는 뜻

**해설**: 이 패턴만 익혀두면 볼 때마다 "아, 뭔가 아직 준비가 안 된 상태구나"를 바로 알아챌 수 있어요.

**Q7** (compare)
> 이 에러를 AI에게 전달할 때 더 나은 방식은?
>
> **A** `"값이 없대요"`
> **B** `"Cannot read property 'price' of undefined 에러가 나는데, 상품 데이터가 아직 안 와서 그런 것 같아요"`
- ① A
- ② B ✓

**해설**: 에러 메시지와 함께 본인의 추측까지 덧붙이면 AI가 원인 파악에 훨씬 도움을 받아요.

## 4-3. 화면이 하얗게 뜰 때

**Q1** (choice)
> 브라우저 화면이 아무것도 없이 하얗게 됐습니다. 가장 먼저 할 일은?
- ① 컴퓨터를 끈다
- ② 콘솔(개발자도구)을 열어서 에러가 있는지 확인한다 ✓

- ④ 프로젝트를 삭제한다

**해설**: 대부분 코드 어딘가에서 에러가 나서 화면 그리기가 멈춘 거예요. 콘솔을 열면 이유가 나와 있어요.

**Q2** (choice)

> ```

>   at ProductList.jsx:12
> ```
- ① `ProductList.jsx` 파일의 12번 줄 근처에서 문제가 생겼다 ✓
- ② 인터넷이 끊겼다
- ③ 컴퓨터 용량이 부족하다
- ④ 아무 정보도 알 수 없다

**해설**: 파일명과 줄 번호가 나와 있으면 그 위치부터 살펴보면 돼요.

**Q3** (choice)

- ① 화면이 하얗게 뜨는 쪽 — 콘솔에 명확한 에러가 남는 경우가 많아서 ✓
- ② 일부만 이상한 쪽 — 항상 더 명확해서
- ③ 둘 다 항상 똑같이 어렵다
- ④ 둘 다 원인을 알 수 없다

**해설**: "일부만 이상한" 경우는 에러 없이 조용히 잘못될 수도 있어서 오히려 찾기 까다로울 때가 있어요.

**Q4** (order)

- 에러 메시지를 AI에게 보여주기

**정답 순서**: 1 → 2 → 3

**해설**: 무작정 "안 돼요"라고 하기 전에 정보를 확인하고 전달하면 훨씬 빠르게 해결돼요.

**Q5** (choice)
> 화면이 하얗게 됐는데 콘솔에도 에러가 안 보입니다. 다음으로 확인할 것은?
- ① 서버(터미널)가 실행 중인지, 터미널 자체에 에러가 없는지 ✓
- ② 포기하고 컴퓨터를 재부팅한다
- ③ 인터넷 공유기를 재시작한다
- ④ 다른 컴퓨터로 옮긴다

**해설**: 브라우저 콘솔이 아니라 터미널에서 문제가 날 때도 있어요. 두 군데 다 확인하는 습관이 필요해요.

**Q6** (choice)

- ② 에러가 아니라는 뜻
- ③ 경고일 뿐 무시해도 된다는 뜻
- ④ 곧 자동으로 고쳐진다는 뜻

**해설**: 화면이 하얗게 되는 것과 자주 함께 나타나요.

- ② B ✓

**해설**: 정보 없이 "안 돼요"만 전달하면 AI도 추측만 할 수밖에 없어요.

## 4-4. 콘솔 열어보는 법

**Q1** (choice)
> "콘솔을 열어서 확인해보세요"라는 말을 들었습니다. 콘솔은 어디서 여나요?
- ① 브라우저에서 F12 (또는 우클릭 → 검사) ✓
- ② 에디터(Cursor, VS Code)에서
- ③ 터미널에서
- ④ 휴대폰 설정에서

**해설**: 콘솔은 브라우저의 "개발자도구" 안에 있는 탭이에요.

**Q2** (choice)
> 개발자도구의 여러 탭 중 에러 메시지를 확인하려면?
- ① Elements
- ② Console ✓
- ③ Network
- ④ Sources

**해설**: `Console` 탭에 에러, 경고, 코드에서 찍은 로그들이 나타나요. 빨간 글씨가 보통 에러입니다.

**Q3** (choice)
> 콘솔의 빨간 글씨와 노란 글씨의 차이는?
- ① 빨간색은 멈출 정도의 심각한 문제(에러), 노란색은 주의가 필요하지만 계속 동작하는 경고 ✓
- ② 색깔은 아무 의미 없다
- ③ 노란색이 더 심각하다
- ④ 둘 다 똑같이 심각하다

**해설**: 둘 다 살펴보는 게 좋지만, 에러가 화면이 멈춘 직접적 원인일 가능성이 높아요.

**Q4** (blank)
> 브라우저에서 개발자도구를 여는 단축키는?
> ```
> Windows: ___
> ```
- ① `F12` ✓
- ② `Ctrl + S`
- ③ `Alt + Tab`
- ④ `Enter`

**해설**: Windows는 `F12`, Mac은 `Cmd + Option + I`로 열 수 있어요.

**Q5** (choice)
> 콘솔에 메시지가 너무 많아 뭐가 중요한지 모르겠습니다. 좋은 방법은?
- ① 빨간색(에러)부터 위에서 아래로 하나씩 읽어본다 ✓
- ② 전부 무시한다
- ③ 콘솔을 닫아버린다
- ④ 메시지 순서를 무작위로 읽는다

**해설**: 경고보다 에러를 먼저 확인하는 게 우선순위예요.

**Q6** (choice)
> 콘솔 우측 상단의 빨간 숫자(예: "3")는 무엇을 의미할까요?
- ① 현재 콘솔에 쌓인 에러의 개수 ✓
- ② 접속한 사람 수
- ③ 남은 배터리
- ④ 페이지 로딩 속도

**해설**: 콘솔을 안 열어봐도 이 숫자로 문제가 있는지 짐작할 수 있어요.

**Q7** (compare)
> AI에게 문제를 설명할 때 더 나은 방식은?
>
> **A** `"화면이 이상해요"`
> **B** `"콘솔을 열어보니 빨간 글씨로 이런 에러가 있어요: [메시지]"`
- ① A
- ② B ✓

**해설**: 콘솔을 확인하는 습관이 있으면 항상 구체적인 정보를 가지고 요청할 수 있게 돼요.

## 4-5. 같은 요청인데 매번 다르게 막힐 때

**Q1** (choice)
> 데이터를 불러오려는데 이 에러가 떴습니다. 무슨 뜻일까요?
> ```
> Access to fetch at 'https://api...' has been blocked by CORS policy
> ```
- ① 인터넷 연결이 끊겼다
- ② 요청은 보냈지만, 브라우저가 보안상의 이유로 응답을 막았다 ✓
- ③ 서버가 꺼져 있다
- ④ 코드에 오타가 있다

**해설**: 브라우저는 "내가 보고 있는 사이트와 다른 주소"로 보낸 요청의 응답을 기본적으로 막아요.

**Q2** (choice)
> CORS 에러가 유독 자주 나는 상황은?
- ① 내 프로젝트 안에서 데이터를 저장하고 불러올 때
- ② 서로 다른 주소(도메인)의 서버에 데이터를 요청할 때 ✓
- ③ 버튼 색을 바꿀 때
- ④ 글자 크기를 조정할 때

**해설**: 프론트엔드와 백엔드(또는 외부 API)의 주소가 다를 때 자주 생겨요.

**Q3** (choice)
> CORS 에러와 "Cannot read property... of undefined" 에러의 차이는?
- ① CORS는 요청 자체가 막힌 것, undefined 에러는 값이 없는 걸 읽으려 한 것 ✓
- ② 둘은 완전히 같은 문제다
- ③ CORS가 더 가벼운 문제다
- ④ undefined 에러가 항상 CORS 때문에 생긴다

**해설**: CORS는 "요청/보안" 문제고, undefined는 "값이 준비 안 됨" 문제라 구분해서 이해하는 게 좋아요.

**Q4** (blank)
> CORS 에러가 났을 때 AI에게 요청할 만한 말은?
> ```
> "CORS 에러가 나는데, ___ 해줘"
> ```
- ① 서버에서 이 주소를 허용하도록 설정 ✓
- ② 인터넷을 다시 연결
- ③ 컴퓨터를 재부팅
- ④ 파일을 삭제

**해설**: CORS는 보통 서버 쪽 설정으로 "이 주소에서 오는 요청은 허용한다"고 등록해줘야 풀려요.

**Q5** (choice)
> 어제까지 잘 되던 게 오늘 CORS 에러를 냅니다. 가장 가능성 **낮은** 원인은?
- ① 서버 주소나 설정이 최근에 바뀌었다
- ② 갑자기 컴퓨터 CPU가 느려져서 ✓
- ③ 배포 환경이 바뀌면서 허용 설정이 달라졌다
- ④ 로컬 서버를 재시작하면서 설정이 초기화됐다

**해설**: CORS는 속도나 성능과 관계없는 "허용 여부" 문제예요.

**Q6** (choice)
> "blocked by CORS policy"를 보면 어떤 첫인상을 가져야 할까요?
- ① "요청이 보안 규칙에 막혔구나, 서버 쪽 허용 설정을 봐야겠다" ✓
- ② "인터넷이 아예 끊겼구나"
- ③ "코드에 오타가 있구나"
- ④ "컴퓨터를 재부팅해야겠다"

**해설**: 이 패턴을 익혀두면 다음에 또 만나도 당황하지 않고 방향을 잡을 수 있어요.

**Q7** (compare)
> CORS 에러가 났을 때 더 나은 대응은?
>
> **A** 에러를 무시하고 새로고침만 반복
> **B** 에러 메시지를 보여주고 "CORS 문제 같은데 서버 설정을 봐달라"고 요청
- ① A
- ② B ✓

**해설**: CORS는 새로고침으로 해결되지 않아요. 원인을 짚어서 고쳐야 하는 문제예요.

## 4-6. 이 에러, AI에게 뭐라고 보여줄까

**Q1** (choice)
> AI에게 에러를 전달할 때 가장 도움이 되는 조합은?
- ① 에러 메시지 전체 + 무엇을 하다가 났는지 + 관련 코드 ✓
- ② "에러 나요"라는 말 한마디
- ③ 에러가 난 시각
- ④ 컴퓨터 사양

**해설**: 메시지(무슨 에러), 상황(뭘 하다가), 코드(어디서)가 갖춰지면 AI가 원인을 훨씬 정확히 짚어줘요.

**Q2** (choice)
> 아래 두 요청 중 앞서 배운 내용을 더 잘 반영한 것은?
> ```
> A: "장바구니 페이지에서 상품 추가 버튼 누르면
>     'Cannot read property price of undefined' 에러가 떠요.
>     아마 상품 데이터가 아직 안 온 상태인 것 같아요."
>
> B: "장바구니 안 돼요"
> ```
- ① A ✓
- ② B

**해설**: A는 상황, 정확한 에러 메시지, 본인의 추측까지 다 담겨 있어요.

**Q3** (choice)
> 에러 전달 시 "본인의 추측"까지 덧붙이면 좋은 이유는?
- ① 틀려도 AI가 방향을 좁히는 데 참고가 되기 때문 ✓
- ② 추측이 항상 정답이기 때문
- ③ 안 써도 되지만 예의상 넣는 것
- ④ AI가 추측을 요구하기 때문

**해설**: 틀려도 괜찮아요. "이 사람이 어디까지 이해했는지"를 AI가 파악하는 데 도움이 돼요.

**Q4** (order)
> 에러를 AI에게 전달하는 좋은 순서는?
- 상황 설명 (무엇을 하다가)
- 정확한 에러 메시지 붙여넣기
- 본인 추측 (있다면)

**정답 순서**: 1 → 2 → 3

**해설**: "뭘 하다가 → 무슨 에러가 → 왜 그런 것 같다"의 흐름이 자연스러워요.

**Q5** (choice)
> 에러 메시지를 일부만 잘라서 전달했더니 AI가 엉뚱한 해결책을 줬습니다. 원인은?
- ① 메시지 뒷부분에 중요한 정보(파일 위치 등)가 잘려나갔을 가능성 ✓
- ② AI가 원래 이상하게 대답해서
- ③ 질문을 너무 길게 해서
- ④ 이유 없음

**해설**: 에러 메시지는 가능하면 전체를 그대로 복사하는 게 좋아요.

**Q6** (choice)
> 4단계 전체를 한 문장으로 요약하면?
- ① 에러는 무시해야 할 대상이다
- ② 에러는 읽고, 위치를 확인하고, 정확하게 전달해야 할 정보다 ✓
- ③ 에러가 나면 무조건 처음부터 다시 만들어야 한다
- ④ 에러는 항상 AI 잘못이다

**해설**: 이 감각이 있으면 막히는 순간마다 혼자 해결하는 속도가 빨라져요.

**Q7** (compare)
> 앞으로 에러를 만났을 때 더 도움이 되는 태도는?
>
> **A** "또 막혔네, 처음부터 다시 만들어야겠다"
> **B** "에러가 났네, 메시지 읽고 위치 확인하고 정확히 전달해보자"
- ① A
- ② B ✓

**해설**: 막힘은 프로젝트가 끝났다는 신호가 아니라, 다음 단계로 넘어가기 위한 평범한 과정이에요.

# 5단계. AI에게 제대로 요청하기

## 5-1. 구체적으로 요청하기

**Q1** (choice)
> 실제로 각각 요청해서 나온 결과입니다. A의 결과가 "예상과 다를 수 있는" 이유는?
> ```
> 요청 A: "버튼 예쁘게 해줘"
>   → 파란 그라데이션 + 둥근 모서리로 변경됨
>
> 요청 B: "버튼을 회사 로고 색(#FF6B35)으로, 모서리는 각지게 해줘"
>   → 정확히 그 색과 모양으로 변경됨
> ```
- ① AI가 임의로 이상하게 만들어서
- ② "예쁘다"의 기준을 AI가 자체적으로 판단해서 채웠기 때문 ✓
- ③ 그라데이션은 항상 별로라서
- ④ 버튼 요청은 원래 안 되는 요청이라서

**해설**: 추상적인 기준은 AI가 알아서 채워요. 그 판단이 내 생각과 맞을 확률은 낮습니다.

- ① 버튼을
- ② 지금보다 크게, 가로 폭을 화면 전체로 ✓
- ③ 늘려줘
- ④ 없음

**해설**: 비교 기준이나 범위를 명시한 부분이 구체성을 만들어요.

**Q3** (choice)
> "빠르게 해줘"라는 요청이 모호한 이유는?
- ① 속도의 기준이 사람마다 다르고, 무엇이 빠르길 원하는지도 불분명해서 ✓

- ③ 원래 안 되는 요청이라서
- ④ 문법이 틀려서

**해설**: 로딩 속도인지, 응답 속도인지, 애니메이션 속도인지도 짚어줘야 해요.

**Q4** (blank)

> ```

- ③ 멋진
- ④ 알아서

**해설**: 위치는 구체적인 방향으로 짚어줘야 AI가 정확히 반영해요.

**Q5** (choice)

- ③ 존댓말이 아니라서
- ④ 영어가 아니라서

**해설**: 이런 요청은 AI가 큰 폭으로 바꾸다가 예상 못한 곳까지 건드릴 위험이 커요.

**Q6** (choice)
> 결제 화면을 요청하면서 하나만 덧붙일 수 있습니다. 코드에 가장 직접적으로 반영될 정보는?

- ③ "사용자가 좋아했으면 좋겠어요"

**해설**: 배경이나 바람은 코드로 옮길 방법이 없어요. 구체적 동작 조건만 반영됩니다.

- ① A

**해설**: B는 무엇을, 어디에 추가할지가 명확해요.

## 5-2. 작게 나눠서 요청하기

**Q1** (choice)

- ② 네 가지를 한 번에 요청해서, 어느 부분의 코드가 이 에러와 관련 있는지 구분이 안 되기 때문 ✓

- ④ 마이페이지 자체가 원래 어려운 기능이라서

**해설**: 한 번에 여러 걸 바꾸면 문제가 생겼을 때 원인 범위를 좁히기 어려워요.

**Q2** (choice)

**해설**: 한 가지 화면, 한 가지 기능 단위로 요청하는 게 "작게 나누기"예요.

**Q3** (choice)

- ① 문제 생겼을 때 원인 찾기 쉬움

- ③ 앱이 저절로 더 빨라짐 ✓
- ④ 각 단계마다 방향을 조정할 수 있음

**해설**: 나눠서 요청하는 건 "관리하기 쉬움"과 관련 있지, 앱 실행 속도와는 상관없어요.

**Q4** (blank)
> 빈칸에 알맞은 단위는?
> ```
> 큰 기능 하나를 통째로 요청하기보다, ___ 단위로 나눠서 요청한다
> ```
- ① 화면 하나, 기능 하나 ✓
- ② 프로젝트 전체
- ③ 한 달치
- ④ 랜덤

**해설**: 화면 단위나 기능 단위로 쪼개는 게 실용적인 기준이에요.

**Q5** (choice)
> "회원가입, 로그인, 게시판을 한 번에 다 만들어줘"의 문제는?
- ① 세 가지 중 어디서 에러가 났는지 헷갈린다 ✓
- ② AI가 아예 대답을 안 한다
- ③ 세 가지가 저절로 합쳐져서 하나가 된다
- ④ 비용이 3배로 명확히 계산된다

**해설**: 결과를 확인할 때도 뒤섞여서 어디를 봐야 할지 헷갈려요.

**Q6** (choice)
> 작게 나누는 습관이 4단계(에러)와 어떻게 이어질까요?
- ① 무관하다
- ② 작게 나누면 에러가 나도 원인 범위가 좁아 대응이 빨라진다 ✓
- ③ 작게 나누면 에러가 절대 안 난다
- ④ 작게 나누면 에러 메시지가 안 보인다

**해설**: 작은 단위로 요청했으면 에러가 나도 "방금 그 요청 때문"이라는 걸 바로 알 수 있어요.

- ② B ✓

**해설**: B는 각 단계마다 확인하며 진행하니 문제가 생겨도 바로 잡을 수 있어요.

## 5-3. AI가 이상한 답을 줄 때 알아채기

**Q1** (choice)
> AI가 준 코드를 실행했더니 이런 에러가 났습니다. 가장 정확한 해석은?
> ```js
> import { useMagicState } from 'react'
> ```
> ```
> SyntaxError: The requested module 'react' does not provide
> an export named 'useMagicState'
> ```
- ① 내 컴퓨터에 문제가 있다
- ② AI가 실제로 react에 없는 함수를 마치 있는 것처럼 만들어냈다 ✓
- ③ react 버전이 너무 낮아서 생긴 문제다
- ④ import 순서가 잘못됐다

## 5-4. "왜 이렇게 짰어?" 물어보는 습관

>   fetchData()

- ④ 파일 저장 위치

## 5-5. 대화가 꼬였을 때

**Q1** (choice)
> 같은 대화창에서 20번째 요청을 하는 중 이런 일이 있었습니다. 이 상황이 나타내는 신호는?
> ```
> 요청: "장바구니 페이지의 여백만 조금 줄여줘"
> 결과: 여백은 그대로고, 대신 3번째 요청 때 만들었던
>       로그인 기능이 통째로 사라짐
> ```
- ① AI가 오늘따라 실수한 것뿐, 계속 같은 대화로 진행해도 된다
- ② 대화가 길어지며 AI가 이전 맥락을 헷갈리기 시작했다는 신호 — 새 대화가 필요할 수 있다 ✓
- ③ 여백 요청이 잘못된 요청이었다
- ④ 컴퓨터를 재부팅해야 한다

**해설**: 대화가 길어질수록 AI가 참고해야 할 맥락이 많아져서 헷갈리기 쉬워요.

**Q2** (choice)
> "대화가 꼬였다"는 신호로 볼 수 있는 것은?
- ① AI가 방금 한 요청과 전혀 다른 걸 자꾸 고친다 ✓
- ② AI가 빠르게 답한다
- ③ 코드에 주석이 많다
- ④ 질문이 짧다

**해설**: 요청과 결과가 계속 어긋나기 시작하면 맥락이 꼬였다는 신호일 수 있어요.

**Q3** (choice)
> 새 대화를 시작할 때 좋은 방법은?
- ① 아무 설명 없이 바로 새 요청만 한다
- ② 지금까지 뭘 만들었고 지금 뭘 하려는지 간단히 요약해서 알려준다 ✓
- ③ 이전 대화 전체를 복사해서 통째로 붙여넣는다
- ④ 새 대화는 의미가 없다

**해설**: 짧은 요약만으로도 AI가 다시 맥락을 잡는 데 충분한 경우가 많아요.

**Q4** (blank)
> 빈칸에 알맞은 것은?
> ```
> 같은 실수가 반복되고, 요청할 때마다 결과가 이상해진다 → ___ 고려
> ```
- ① 새 대화 시작 ✓
- ② 컴퓨터 재부팅
- ③ 인터넷 재연결
- ④ 프로젝트 삭제

**해설**: 이 신호가 보이면 새 대화가 문제 해결의 실마리가 될 수 있어요.

**Q5** (choice)
> 새 대화로 옮기기 전에 미리 해두면 좋은 것은?
- ① 지금까지 진행 상황을 파일이나 메모로 정리해두기 ✓
- ② 아무것도 준비할 필요 없음
- ③ 프로젝트 삭제
- ④ 인터넷 끊기

**해설**: 정리해두면 새 대화 시작 시 그대로 붙여넣어 빠르게 맥락을 전달할 수 있어요.

**Q6** (choice)
> 대화를 새로 시작하는 것에 대한 올바른 인식은?
- ① 실패를 인정하는 것
- ② 맥락을 정리하고 다시 효율적으로 진행하기 위한 정상적인 방법 ✓
- ③ 절대 해서는 안 되는 것
- ④ AI가 고장났다는 뜻

**해설**: 새 대화 시작은 실패가 아니라 효율을 되찾는 자연스러운 방법이에요.

**Q7** (compare)

- ② B ✓

**해설**: A는 시간이 갈수록 더 꼬일 수 있어요. B처럼 리셋하는 게 결과적으로 빨라요.
